# Agentflow — 白話使用手冊

這一頁用日常語言解釋 agentflow 怎麼用，並附上例子。它假設你從來沒用過這套系統。給 AI 看的規則書放在 `SKILL.md`；你完全不需要讀那個檔案就能使用整套系統。

## 一切背後只有一個核心概念

- **你和 AI 透過一本筆記本檔案交談，而不是透過終端機。** 這個檔案叫 `devlog.md`，就放在你的專案資料夾裡。

- 你把請求寫進筆記本。AI 做完工作後，把答覆寫進同一本筆記本、你的請求正下方。你們兩邊說過的每一句話，都留在頁面上。

- 為什麼用檔案而不用終端機：終端機會忘記，檔案會記得。每個決定、每個問題、每個結果都存進 Git（版本控制系統，會保存檔案的每一版歷史），所以你隨時、在任何電腦上，都能回頭讀完整段歷史。

## 開始使用 — 一個字

1. 在終端機打開你的專案資料夾，啟動 AI（例如執行 `claude`）。

2. 輸入一個字 `godev`，按下 enter。

3. **在一個專案裡第一次使用時：** AI 會幫你建立 `devlog.md`。檔案最上方會印出一行設定值，長得像這樣：

	```
	Settings: target_doc=devlog.md, lang=English, auto_reply=off, ask_names=off, cli_provider=any, runlog=on
	```

	檔案最下方還會留一個空的「Ask」（提問）區塊。那個空區塊就是你下一次輸入請求的地方。

	它還會問你一個小問題：「這個專案要用什麼簡短代號？」— 見下面的「幫專案取個小名」一節。

	**如果你的資料夾還沒被 Git 管理**（Git 是保存檔案每個版本的存檔系統，有它在，任何東西都不會弄丟），AI 會多問一個問題：「要幫你設定好嗎？」建議答案是「要」— 有了 Git，每一輪工作都會被安全存檔，就算程式中途當掉，AI 也能靠存檔找回完整經過。它絕不會不問你就自己動手設定。

4. **之後的每一次：** `godev` 的意思就是「去看筆記本，然後繼續」。AI 會讀檔案，找到你最新的請求或還沒回答的問題，然後開始工作。

## 幫專案取個小名 — 讓你隨時知道自己在哪本筆記本裡

- **這個功能解決的問題：** 當你同時在好幾個專案裡工作時，每本筆記本都叫 `devlog.md`，長得一模一樣。很容易打開錯的那本，把請求寫進錯的專案。

- **筆記本第一次建立時，AI 會問你一個問題：** 這個專案要用什麼簡短代號？它會建議用專案資料夾的名字當預設值，所以回答「yes」就夠了。

- **你的答案會永久存在筆記本最上方的 STATUS 區塊裡。** 長得像這樣 — 一個簡短的英文代號，加一行你喜歡的任何語言的描述：

	```
	Project: aglite — agentflow 技能與它的使用手冊
	```

- **隨時可以改**：在請求裡用日常語言講一聲就好，沒有特殊語法要學。

## 筆記本可以改名 — 做到一半也行

- **這個功能解決的問題：** 上面的專案小名要打開檔案才看得到，但編輯器的分頁列上還是五個一模一樣的 `devlog.md`。如果你想讓檔名本身就說出這是哪個專案，就幫筆記本改名。

- **怎麼改名：** 在請求裡任何位置寫一行 — `target_doc: ag.devlog.md` — 填上你想要的新名字。整個程序就這一行。AI 會用保留完整歷史的方式改檔名，把封存檔一起改成配套的名字，並在答覆裡用「舊名 → 新名」跟你確認。

- **建議的命名形狀：專案代號放前面，保留 `devlog` 這個字。** 例如 `ag.devlog.md` 或 `shop.devlog.md`。編輯器分頁一眼就能分辨，而且任何人瞄一眼資料夾，仍然認得出這是一本筆記本。

- **那新開的工作階段跑去找 `devlog.md` 怎麼辦？** AI 會在舊地址留一張一行字的轉寄卡，就像搬家後郵局留的轉址通知：`Moved to: ag.devlog.md — write your asks there.`（已搬到 ag.devlog.md — 請去那裡寫需求。）新的工作階段找到卡片、照著走，就接上真正的筆記本。它絕不會在你改名後的筆記本旁邊再建一本空的。

- **如果有人不小心把請求寫進轉寄卡裡**，它一樣會被回答 — AI 會把文字搬進真正的筆記本，並註明這個小插曲。任何請求都不會遺失。

- **提到舊名字的舊頁面維持原樣。** 它們是歷史，歷史永不改寫。筆記本的 STATUS 區塊會多一行紀錄這次改名，像 `Renamed: devlog.md → ag.devlog.md (2026-08-14)`。

## 每句話都要打 `godev` 嗎？

- **不用。每個工作階段只要打一次。** 工作階段（session）指的是你在終端機裡跑 AI 程式的一次執行。第一次打完 `godev` 之後，筆記本協定在整個工作階段都保持開啟 — 你接下來說的每句話都在協定下處理，並記錄進 `devlog.md`。

- **開新的工作階段時才要再打一次** — 開新的終端機視窗、重新啟動程式、或清除對話之後。還是同一個字，而且它同時代表「從上次停下的地方繼續」，所以工作階段之間不會遺失任何東西。

- 第一次 `godev` 之後，你有兩種說話方式，兩種都可以：

	- **直接在終端機打字。** AI 做完工作，把請求和答覆都記進筆記本。

	- **直接寫進筆記本。** 打開 `devlog.md`，把請求寫進最下方的空 Ask 區塊，存檔，然後在終端機打 `godev` 或 `continue`，意思是「我寫了東西 — 去讀」。

## 一輪對話長什麼樣子

- 你的請求會拿到一個編號，像 `A-007`。AI 的答覆出現在正下方，標著同一個編號。一個請求加一個答覆，稱作一輪（round）。

- 當 AI 需要你做決定時，它絕不會在工作中途打斷你。它把所有問題收集在答覆的最後面，每個問題下面寫一個建議答案，再留一行空白像這樣：

	```
	- ans:
	```

- 你把答案打在 `ans:` 後面，存檔，打 `godev`。AI 讀了你的答案就繼續工作。如果你同意它的建議，回答一個「yes」就夠了。

## 六個設定 — 它們是什麼、怎麼看、怎麼改

設定總共有六個。你可以完全不碰它們；預設值就能用。但它們永遠看得到，而且永遠只差一行字就能改。

- **怎麼看：** 設定行就放在 `devlog.md` 最上方的 STATUS（現況）區塊裡，每一輪結束都會更新。或者打一個字 `settings` — AI 會在筆記本裡寫一張卡片，列出每個設定的名字、目前的值、一句話說明它做什麼、以及要改它時該打的那一行字。

- **怎麼改：** 在你的請求裡任何位置寫一行像 `auto_reply: on` 的字。AI 會在答覆裡用「舊值 → 新值」的形式跟你確認。

- **每個設定的意思：**

	- **`target_doc`** — 哪個檔案是筆記本。預設值：專案根目錄的 `devlog.md`。你很少需要親手改它；下面介紹的團隊功能會幫你管理。

	- **`lang`** — AI 書寫時用的語言（答覆、文件、提交訊息都算）。第一次使用時會自動偵測你電腦的系統語言。要改就寫一行像 `lang: 繁體中文`。

	- **`auto_reply`** — AI 可不可以自己回答自己提出的例行問題、不等你就繼續工作？`off`（預設值）表示每個問題都等你。`on` 表示它採用建議答案繼續做 — 你讓它整晚自己工作時很有用。但有四件事不管怎麼設都一定停下來等你：只有主人能做的決定、無法復原的事、會透過新管道離開你機器的事、超過約定花費上限的事。

	- **`ask_names`** — 每個請求的標題要不要顯示是誰寫的？`off`（預設值）只顯示編號，像 `# → Ask / A-018`。`on` 會加上提問者的名字，像 `# → Ask / A-018 (John)` — 好幾個人共用同一本筆記本時很有用。AI 會優先用你在請求裡自己說的名字；沒說的話用你的 Git 名字；最後才用電腦的登入帳號名。

	- **`cli_provider`** — 「誰來做這些工作」的單一開關。它有四個值：

		- **`any`**（預設值）— AI 自己一件一件判斷該派給誰做，而且它可以雇用你機器上已經裝好的外部 AI 程式（像 `codex`）當額外工人。這就是平常、每天的一般行為。

		- **`off`** — 不管在哪台機器上，都只用內建工人。AI 仍然一件一件判斷要外包什麼，但它絕不會啟動「別家公司」的程式。有一個很窄的例外是為了保住安全：當某件工作真的需要被隔離的工人、而內建工人做不到足夠的隔離時，AI 可以只為那一件工作，使用你「同一家公司」自己的命令列程式（例如你啟動的是 Codex 時，用 `codex exec`）純粹當作隔離用的籠子 — 它從頭到尾不會超出你那一份訂閱。如果連這樣都做不到需要的隔離，AI 會停下來問你，而不是用不安全的方式硬做。

		- **`codex`** 或 **`claude`** — 「全外包」設定。你啟動的那個 AI 只當管理者：它負責寫工單、親手驗收每個成果、寫筆記本和報告 — 而所有實際的勞務（寫程式、寫文件、查資料）全部交給那個指定家族的更便宜的工人去做。當你想用一個強的模型監工、讓便宜的家族做所有粗活時，就用它。只有真正微小的修改會留給管理者自己做，而且每次它都會在答覆裡說明。

		- **一個值得知道的安全細節：** 有些檢查偏好由「不同公司」的第二個 AI 來覆核第一個（叫「跨家族」覆核）。大多數人只有一家訂閱，所以當你的設定讓「不同公司的工人」一個都沒有 — 也就是 `off`、或是一個和你啟動的那個 AI 同公司的家族名 — 覆核仍然會進行：改由你自己這家公司「最強」的模型來做，而且是全新啟動、記憶全空，所以它不會沿用第一個 AI 的盲點；它也絕不會是「做那件工作的同一個 AI」自己檢查自己。這種替換一定會寫進筆記本的回覆裡，絕不偷偷進行。

	- **`runlog`** — 在跑完整開發工作時，AI 要不要多留一份給機器讀的事件記錄？`on`（預設值）表示它會寫一個 `runlog.md`，詳細記下它雇用過的每個工人、每次檢查結果、每個自動答覆 — 想事後稽核到底發生了什麼時很有用。`off` 表示它跳過那個檔案；不管哪一種，你平常的筆記本（`devlog.md`）都仍然是完整的人類記錄。這個設定只在跑完整開發工作時才有作用；純粹問問題和小雜務時，從來不會產生這種記錄。你也可以寫 `runlog: false` 當作 off、`runlog: true` 當作 on。

## 全力以赴 — 用 `all_in` 要求一件工作跑完整流程

- **它解決的問題：** 面對小工作，AI 是被允許抄捷徑的 — 跳過選配的檢查步驟、縮減文書 — 這樣你就不必為一行小修改付出整套儀式的成本。但有時候一件工作「看起來」小，實際上很重要，你希望每個檢查都跑、每份文件都寫，完全不准抄捷徑。

- **怎麼要求：** 在你的請求裡任何位置放上 `all_in` 這個詞（帶底線）。例如：「go `all_in` on this job：幫發票頁面加一個刪除按鈕。」底線就是它成為指令的關鍵 — 一般英文句子裡的 "all in" 兩個字不會有任何作用，所以日常語句永遠不會誤觸它。

- **這個詞保證的事，一條不少：** 完整開發流程一定跑；AI 不可以提議或採用任何捷徑路線；每個選配的檢查步驟都要跑（風險探索、技術實驗、安全掃描、經驗教訓記錄）；每個必跑步驟都不准縮水 — 全深度執行，留下完整文件。

- **它只涵蓋那一個請求。** 下一個請求回到平常模式，由 AI 依工作大小決定力道。事後沒有任何設定需要關掉。

## 一個人一次做一件事 — 什麼都不用特別做

- 直接把你想要的東西寫進筆記本。例如：

	```
	+ 請做一個把字串反轉的小工具，附測試。
	```

- AI 規劃、實作、測試、回報 — 全都在筆記本裡。這件工作完成後，它的對話頁會搬進該功能自己的資料夾，主筆記本保持簡短好讀。

## 同時做多個功能、或團隊合作 — 筆記本會自己分家

整個功能用一句話講完：**當好幾件工作同時進行時，每件工作會拿到自己專屬的筆記本、放在自己的資料夾裡，而主 `devlog.md` 變成一張目錄，指向所有這些筆記本。**

你永遠不用建資料夾，也永遠不用學任何路徑規則。實際用起來像下面這樣。

- **例子：** 你和一位隊友共用一個專案。你在自己的 Git 分支（branch，可以想成專案的平行副本，做完再合併回來）上做登入頁；隊友在另一個分支上做搜尋框。

- **第一步 — 用日常語言說你要什麼。** 在主筆記本（或終端機）寫下類似這樣的話：

	```
	+ 我要在這個分支開始做登入頁。幫它開一本獨立的 devlog — 我隊友同時在做搜尋功能。
	```

	怎麼講都可以，沒有咒語要背。就算你什麼都沒說，AI 也會自己注意到平行工作的跡象（例如你正在功能分支上，或已經有另一件工作在進行中），然後主動問你：「要幫這件工作開一本獨立筆記本嗎？」— 你回答 yes 或 no 就好。

- **第二步 — AI 把一切建好。** 它建立該功能的資料夾、在裡面放一本全新的 `devlog.md`、把你的請求一字不改地抄進新筆記本、並在主筆記本留一行字說明新筆記本放在哪裡。你看著它做；你什麼都不用動。

- **第三步 — 你照原本的方式繼續交談。** 在你的分支上，你只要打 `godev`。AI 會檢查你在哪個分支，自己打開正確的筆記本。你永遠不用記路徑。如果它真的無法確定你指的是哪件工作 — 比如同一個分支上有兩件工作 — 它會問你一個問題，而不是亂猜。

- **不小心寫錯檔案？沒關係。** 你寫在哪裡，AI 就在哪裡回答，並且指出這個小錯位。請求絕不會因為打錯地方而遺失。

- **合併（merge）那天 — 沒有任何事要做。** 你的筆記本和隊友的筆記本住在不同資料夾，所以 Git 把它們並排合起來，完全不衝突。合併之後，AI 會更新主筆記本裡的目錄，把兩件完成的工作都列上去。

- **團隊固定都這樣工作的話：** 在主筆記本的 STATUS 區塊寫一行 `streams: always`，意思是「以後每件工作都自動開自己的筆記本，不用每次問」。設一次，永遠有效。

## 開始做新功能時，需要開新分支或 worktree 嗎？

簡短回答：**通常不用。** 分支、worktree、獨立筆記本是三個各自獨立的工具，每一個都是可用可不用。下面說明每個工具是什麼、什麼時候才值得用。

- **一個人一次做一件事 — 直接寫下願望就好。** 待在原地，把請求寫進筆記本，就這樣。不用分支、不用 worktree、不用獨立筆記本。功能完成後，它的對話頁會自動歸檔進該功能自己的資料夾。

- **分支（branch）** 是同一個專案裡的一條平行歷史線。在分支上做的工作不會干擾任何人，直到你把它合併回來；功能做壞了也可以便宜地整條丟掉。當工作是實驗性的、會做很久的、或和別人的工作同時進行時，才需要開分支。

- **獨立筆記本（stream devlog）** 讓一個功能的對話住在自己的檔案裡。恰恰是「兩段對話會在同一個檔案裡混在一起」的時候才需要它 — 也就是平行工作的情況。在筆記本裡說一句「開新分支＋獨立 devlog」就夠了；AI 會把兩樣都建好，你永遠不用打路徑。

- **worktree** 是磁碟上的第二個實體資料夾，顯示同一個專案的另一條分支。沒有它，切換分支時你唯一的資料夾裡的檔案會來回替換；有了它，兩條分支同時攤在磁碟上、各占一個資料夾。它只在兩種情況下真正有用：你想在主資料夾繼續自己的工作、同時讓 AI 工人在另一個資料夾蓋新功能；或者你在兩件工作之間切換得太頻繁、檔案不停替換讓你受不了。除此之外它只是多餘的重量 — 多一個要記得的資料夾，而且很容易在錯的資料夾裡打指令。另外值得知道：AI 雇用的寫程式工人本來就會自動拿到自己的拋棄式 worktree 當安全籠 — 這個好處你不用開口就有。

- **口訣：** 一個人、一件接一件 → 直接寫願望。和任何人平行工作 — 不管是真人還是背景的 AI 工人 — → 說「開新分支＋獨立 devlog」。只有想讓兩個資料夾同時攤在磁碟上時，才加一句「worktree」。

## 哪些 AI 模型跑得動 agentflow — 實測結果，不是猜的

- 這些建議來自 2026-08-16 的一場實測：每個模型真的跑了 agentflow 的工作，由另一家模型當裁判打分，每個不及格項目都經過人工複查。所有受測模型的「安全行為」全部過關（拒絕藏在檔案裡的惡意指令、該停就停、誠實回報失敗）；模型之間的差距在「記錄習慣」— 最常見的就是終端機只印一行的規則。

- **用 Claude 訂閱：** 主控模型用最強的旗艦級（`fable-5` / `opus` 級、high effort）— 它把完整流程跑得乾乾淨淨。省錢底線是 `sonnet-5`（medium effort 就夠）：能用，而且它以前需要的那兩句提醒規則（終端機只印一行、設定變更要寫「舊值 → 新值」）現在已經直接寫進技能本文 — 2026-08-16 用更新後的技能重測，`sonnet-5`（medium effort）基本測項全部乾淨過關，不需要任何額外設定。不要用 `haiku` 級模型當主控：實測中它把「筆記本改名」偷偷做成「開一個新檔案」，這會弄斷歷史鏈。

- **用 Codex 訂閱：** 主控模型用 `gpt-5.6-sol`（high effort）— 全部乾淨過關。省錢底線是 `gpt-5.6-luna`，effort 一定要開 MAX（開 medium 它就不再主動問要不要建版本控制）。更舊的 `gpt-5.4` / `gpt-5.5`（high effort）大致也能用，一樣有終端機多印字的毛病。誠實提醒：2026-08-16 用強化後的技能重測，luna 有時仍會往終端機多印一行摘要、有時會蓋錯模型名（該寫 `metadata unavailable` 卻自己編一個）— 如果用 luna 當主控，請打開技能附的 Stop-hook（它從模型外面擋掉多行終端輸出，這個壞習慣就溜不過去）。

- **用 ollama 跑本機模型：** 接線是通的，但實測中小模型（9GB 以下那一級）完全無視這套規矩 — 它像聊天助手一樣回答，從頭到尾不寫筆記本。等有工具訓練、20B 以上的本機模型再認真試。

## 只記四件事的話

- 每個工作階段打一次 `godev`；請求寫在 `devlog.md` 或終端機都行，看你喜歡。

- 在 `- ans:` 那行回答問題；一個「yes」就代表採用建議。

- 打 `settings` 看六個開關；用一行像 `auto_reply: on` 的字改任何一個。

- 要和別人（或 AI 工人）平行做新功能時，說「開新分支＋獨立 devlog」；一個人按順序做，什麼都不用特別做。
