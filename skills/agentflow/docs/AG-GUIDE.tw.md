# Agentflow 9.1.2 — 日常使用指南

[English](AG-GUIDE.md) · 繁體中文

agentflow 把你的需求、決定與答案留在專案裡，並保存足以在另一個工作階段接續的復原資訊。交代目標、成功的例子，以及不能改變的事即可。

Agentflow 9 穩定版的 skill 名稱是 `agentflow`。本指南說明日常用法；[速查表](CHEATSHEET.tw.md)列出全部指令、顧問與設定。

## 先完成一件小事

依[套件 README](https://github.com/agfnow/agentflow#install) 安裝 agentflow，再於專案目錄開啟程式代理並載入 skill。安裝與專案初始化是兩個步驟。

若想先自行建立專案，不必啟動代理：在目標目錄執行 `agf init`，再編輯產生的 `.agentflow/<目錄短名>.devlog.md` 空白提問。命令需要 Node 20+、Git 與可用的 Git 提交身分；若沒有 shell 綁定，可用 `node '<已解析的 skill>/scripts/agf.js' init`。

`agf init --lang zh-TW` 可明確選用繁體中文，也支援英文。它建立缺少的 Git，沿用 HEAD 或建立一次空白初始 commit，再建立設定與紀錄，僅提交設定修改，不呼叫模型、不 push，也不安裝 shell 綁定。完整既有專案會略過且不改寫；不完整或不安全狀態會停止，請交由主代理核對復原。單獨的 `zh` 會保留並使用繁體中文，其他中文語系使用繁體中文並儲存 `zh-tw`；其他有效語系自動改用英文，並儲存 `use-lang: en-us`，供後續流程使用。非 Git 設定仍由主代理處理。詳見[獨立初始化](../references/setup.md#standalone-initialization)。

初始化提交不執行 Git hooks；專案要求 hooks 時請使用主代理設定。若沒有 Codex／Claude CLI，looper 路由保持空白，設定後才能分組執行；一般 `godev` 工作仍可使用。

先交代一件具體工作：

```text
godev 修正 README.md 的安裝連結，並依目前檔案確認範例。
```

你正在對話的代理稱為「主代理」。它理解需求、協調其他代理、檢查成果並保存答案。小任務通常只需要開發筆記 devlog；較大的工作可能需要設計與 tracker。

首次初始化會建立缺少的設定與紀錄，保留既有檔案。它也會在根目錄 `AGENTS.md` 補上後續工作階段載入 agentflow 的指示；受委派代理只處理限定任務，不另啟工作流程。

首次專案初始化也會檢查 `agf`。若不存在，主代理會自動為目前設定的 zsh/bash 或 PowerShell（Windows 為盡力支援，原生行為尚待驗證） 加入簡短的 shell 函式，並明確告知修改了哪些啟動檔；開啟新 shell 後即可使用。

既有指令會保留。缺少 Node 20+、不支援的 shell 或不安全的檔案會回報原因，並提供直接執行指令。詳見[指令設定](../references/setup.md#agf-command-setup)。

你的程式代理必須支援並遵守這項指示。若未自動載入，請自行載入 skill 再送出 `godev`。找不到 skill 時會回報，不會默默安裝。

Git 可選。在尚未使用 Git 的資料夾，主代理會在初始化寫入前詢問是否建立儲存庫；未回答就等待，拒絕則繼續但不使用 Git。

若你同意初始化 Git，或符合首次設定條件的既有儲存庫尚無任何 commit，主代理會建立一次空白初始 commit。明確執行 `new-feature` 時，若 main 尚無 commit，也可使用同一做法。

即使 `auto-commit: off` 也可建立這筆初始 commit，但明確禁止 commit 時不會建立。已暫存與未追蹤檔案都會保留；首次交付只包含已驗證的任務／設定修改，原有無關內容須另經你授權才會納入。

已有 HEAD 就沿用。存在其他 refs 或 Git 狀態不安全時會停止初始提交；提交失敗則保留現場，停止設定或功能準備。禁止 commit 時仍可完成設定，但功能工作目錄需要先有 commit。初始提交本身不授權 push 或發布。

如果只啟動初始化、沒有交代任務，完成後會請你提出下一個需求。精確資格與復原方式見[代理初始化規則](../references/setup.md#first-time-setup)。

## 接續未完成的工作

在同一專案開啟代理，輸入 `godev`。主代理讀取目前需求、已保存問題與復原連結，核對實際檔案及執行中的操作後接續。

主代理依工作路徑與章節載入指示，重用仍在背景中的靜態規則。閒置啟動檢查設定與目前工作；執行、規劃、工作代理及特殊程序在需要時才載入。必要安全檢查維持原樣；不保證縮短時間或降低費用。詳見[載入規則](../SKILL.md#load-only-the-applicable-procedure)。

你可以在聊天回答，也可以填寫問題原位置的 `ans:`。空白答案、建議預設值與等待時間都不代表核准。

新 Reply 問題會將「建議預設值：」獨立成縮排段落，前後各空一行，回答欄位保留在下方。既有歷史不重新排版。

```markdown
- **Q-178-1 — 審查：** 核准這份已檢查的結果嗎？

  建議預設值：是。

  - ans:
```

紀錄缺漏或不符時會回報，不會當作已驗證。沒有未完成工作時，主代理會請你交代下一個需求；閒置啟動不會安排 backlog 工作或新增紀錄。

筆記認領避免互相配合的工作階段同時寫入同一本筆記。遇到其他工作階段的認領，需要交接；標記很舊或沒有回應都不授權搶接。

詳見[代理復原與認領規則](../references/session.md#activate-and-recover)。

## 答案與紀錄在哪裡

預設紀錄目錄為 `.agentflow/`；`ag-dir` 可指定其他安全的專案相對路徑。新筆記通常採工作目錄的短名稱：資料夾 `a002` 會產生 `.agentflow/a002.devlog.md`。既有名稱與歷史會保留。

每輪有「提問」、「回覆」與 `A-001` 之類的識別碼。開頭的「狀態」透過「目前工作」連到未完成事項。你也可以直接在下一個提問填入需求，再啟動代理。

預設 `inline-reply: off`，完整答案留在回覆，聊天最後只顯示收據：

```text
→ 已更新: A-001 | .agentflow/a002.devlog.md
  (~/project/a002)
```

開啟該筆記即可閱讀答案。設為 `inline-reply: on` 可在聊天顯示完整答案；也能明確要求這次答案貼在聊天或終端。只討論未來輸出或單說「給我看」不會改變目的地。

必要通知、阻礙與實際功能交接仍會出現在聊天。包含收據在內的文字標籤，都遵循設定語系。

設計文件交代預期行為、應保留的保證與驗收方式。tracker 列出工作及「復原」資訊；兩者都按需要建立。

工作狀態為 `TODO`、`DOING`、`BLOCKED`、`DONE`。等待檢查、審查或交付時仍是 `DOING`；`DONE` 需要完成證據。

有用的檢查與除錯證據另存並連結，通常在 `.agentflow/.tmp/`。被引用的證據應長期保留，不要因目錄名稱就當暫存垃圾刪除。筆記保留答案、限制與復原連結，不塞入技術日誌。

筆記超過 750 行或你要求時，較早完成的輪次可移入相鄰的單一 `<notebook-stem>.archive.md`。未解決工作與最新完成輪次留在現行筆記。明確重新命名筆記時，也包含其封存檔並保留歷史。

`backlog.md` 保存未來工作：`proposed` 是建議，`deferred` 是已接受但延後。先請主代理檢視並選定事項，再執行；記在裡面不等於授權實作。

`sys-invariants.md` 保存後續修改必須維持的已接受保證。內容修改時，已保存答案與聊天都會有專節通知；只搬路徑則通知搬移。空白登錄表不代表已接受任何保證。

詳見[代理紀錄規則](../references/session.md#round-evidence)與[交付規則](../references/delivery.md)。

## 補充目前工作，或安排後續批次

一般後續訊息會修正或擴充目前工作。直接說明改變，以及它取代哪個先前限制。

想稍後再做，請另送一則訊息：

```text
append-rounds 更新安裝範例。
```

一則訊息就是一個後續批次，即使包含多項工作。`append-tasks` 是完全同義指令；兩者都不會新增 looper 工作。

主代理先完成目前回答、核准關卡與獲准交付，再以各自的提問／回覆處理每批。中斷後可用 `godev` 接續待辦批次；排入工作不會喚醒已停止的主代理。取消時請指明批次。

建立、合併與放棄功能請分開送出。批次混入功能生命週期操作時，既不暫存也不執行；請移除後另送其餘一般工作。

詳見[代理批次規則](../references/batches.md#append-rounds)。

## 這次交流不留紀錄

在訊息加入未引用的 `nolog:`、`noop:`、`off:` 或 `skip:`，這次交流就不讀寫工作流程筆記，也不納入後續摘要：

```text
nolog: 請在聊天說明這項設定。
```

已授權工作仍會執行；`noop:` 不是預演。下一則沒有標記的訊息恢復記錄。引用範例不會啟用標記或模式。

不留紀錄的 append 請求既不排入也不執行，請移除標記後重送。詳見[代理路由規則](../SKILL.md#route-before-records)。

## 選擇任務模式或顧問

一般工作不需要指定模式。主代理會依需求選擇足夠的調查、規劃與檢查。

`fast-lane <task>` 由主代理直接執行，略過一般委派、顧問、新設計／tracker、獨立審查與例行進度段落。仍保留需求記錄、復原、檢查、主代理審查及獲准交付。

`skip-review <task>` 保留一般規劃與執行，只把一般獨立審查改成主代理審查，也包含通常要求的風險邊界審查。

兩種模式都跟隨同一項明確任務，涵蓋修正與接續，完成後失效，不改專案設定。

單獨輸入指令時，須有明確的未完成工作；否則主代理會詢問任務或等待。

明確要求的計畫／審查、設定關卡與功能規則仍適用；`skip-review` 取代先前的審查要求，同一則或之後的新要求則優先。

`grill-me <topic>` 用來做需求訪談。主代理先查看背景，再用小輪問題釐清目標、假設與最值得質疑之處，並根據你的回答追問。

至少有一輪讓你確認或修正理解，重要意圖已清楚就停止。訪談授權討論，也能在 fast-lane 工作中要求使用。

`simple-check [target]` 請全新、獨立的審查者依原始需求質疑既有計畫，並測試具體、較簡單的替代方案。只有目前計畫明確時才可省略目標。

結果為該版本的 PASS、REVISE 或 BLOCKED。即使 `review-order: host`，也不改由主代理自審；沒有可用的獨立審查路徑就維持 BLOCKED。

這不授權實作，也不取代其他檢查與核准關卡。一般規劃／審查會閱讀並套用[同一份檢查表](../references/simple-check.md#check)：保留必要成果與防護、排除未授權範圍，並測試具體、較簡單的替代方案。審查會比較整體負擔，包含操作、注意力與復原成本。這些提醒不新增執行代理或階段。

`browfield <task>` 是針對陌生既有程式碼的八步驟，從探索與追溯規則，走到基準、規格、實作、驗證與保存。這個拼法就是指令名稱。

已有儲存庫不會自動啟用它。不必另裝 skill 或安排八位顧問；一般核准與審查仍適用。詳見[代理 brownfield 程序](../references/browfield.md)。

`advisors: requirements, explore` 可要求聚焦建議。主代理也能針對具體調查缺口選用顧問；建議不授權實作提案，也不要求每個角色另派一位代理。

針對明確的待發布候選版本，`advisors: final-audit` 會在檢查與組裝後評估就緒程度。GO 仍不等於發布授權。全部角色見[速查表](CHEATSHEET.tw.md#命令--依字母排序)；精確選用機制見[代理規則](../references/ag.md)。

## 規劃、檢查、審查與核准

說「先規劃，完成後等我決定」，會保存計畫但不授權實作。說「規劃後實作」，則在重要選擇與設定關卡處理完後允許繼續。

規劃先確保已接受的成果與限制，再找最簡單且足夠的做法。你提供目標與例子，主代理從專案推導技術路徑與檢查，只詢問重要未知事項。

`plan-mode` 預設 `optional`：小而可逆的工作通常不用設計；多項成果、委派或中斷接續需要 tracker；多部分行為變更需要設計。`must` 要求修改前具備兩者；`off` 不建新設計，但可建必要 tracker。已有契約與檢查仍適用。

需求、做法與相依關係已明確且風險低時，由主代理直接規劃。任務或群組多不等於複雜；例如六項寫作／新聞／壓縮工作可由主代理分組，新聞查證仍是執行階段的必要工作。

有重大不確定性、重要架構取捨、跨系統耦合，或安全／隱私／破壞性操作／對外操作邊界變動時，採用 `plan-order`（預設 `external`）。委派規劃路徑優先由 Claude 起草，再由 Codex 質疑、修正並產出最終計畫。明確指定的任務路徑／要求與設定的 `3ways` 優先；設定 `host` 則維持直接規劃。主代理簡記選擇原因，出現新複雜性時重新判斷。

這只調整規劃委派，不免除必要的設計／追蹤文件、審查、檢查或核准關卡。重用適用的計畫、審查與通過證據；交接保持精簡完整，禁止工作者另開代理。Codex 主代理可直接質疑 Claude 草稿，不必再派第二位規劃工作者。

使用 `3ways <request>`，讓 Claude 與 Codex 各自獨立完成盲寫計畫，再比對並交互辯論。雙方都完成前，不得看到對方本次任務的草稿或提示；可共用原始證據與先前已接受的契約。

Codex 負責最終整合，並提出有理由的技術決斷。參與的主代理必須先保存自己的草稿才讀取對方輸出，否則改用全新且未接觸草稿的參與者；不然成果仍屬暫定，不得視為盲寫 3ways。

`plan-order: 3ways` 對已確定需要的規劃（含建議報告）啟用完全相同的程序。不設固定回合上限或最低回合數。

技術異議與 Codex 的最終理由須保留；只有雙方明確接受相同最終內容才算共識。

缺少必要參與者或有效盲寫草稿時，成果仍屬暫定。擁有者專屬決定、必要證據與核准關卡仍有效；這不授予實作核准。參見 [review.md，第 76 行](../references/review.md#3ways-compare-before-implementation)。

外部規劃優先由 Claude CLI 起草，再由 Codex 質疑與整合；Codex 主代理可直接完成後者。原生路徑在支援的原生／主代理控制內優先採同樣角色。

Host 與 fast-lane 由主代理直接規劃，不探測工作者。

偏好角色不可用時須揭露；明確的提供者、模型、effort、獨立性或唯讀要求仍阻擋不相容備援。已選控制無效時需要決定，不會默默替換。

主代理先檢查成果。程式、操作提示、產品成果與可直接實作的契約，通常還要做成果審查；一般問答與例子由主代理檢查。

`review-order` 預設 `external`：對應提供者的 CLI、全新原生代理，最後才是揭露限制的主代理審查。可行時，獨立審查優先選擇與已知主計畫不同的模型家族，再考慮另一個已設定模型。重複或未知身分會揭露，不當作多樣性的證據。

主代理備援不能滿足必要獨立性。即使審查接受原始碼，缺少的必要檢查仍是未證明。

`gate-design: on` 要求實作前核准設計，與 `plan-mode: off` 衝突。`gate-tracker: on` 在有 tracker 時，要求核准已檢查成果後才做最終交付。

兩個關卡預設都是 off。空白答案不算核准；相同且未變的已核准結果不用反覆詢問。詳見[設定速查](CHEATSHEET.tw.md#agjson--switches--依字母排序)、[代理規劃](../references/planning.md#planning-modes-and-gates)與[審查規則](../references/review.md)。

## 分開開發一個功能

Git worktree 是同一儲存庫的另一個工作目錄，擁有自己的分支與檔案。送出 `new-feature search`，會準備 `.wts/ft-search`、分支 `feature/search` 與功能筆記。

main 工作目錄需要先有 commit。準備時可建立前述限定的空白初始 commit，原有無關檔案仍排除。建立本身不授權未交代的實作。

請照實際的編號交接訊息操作。Codex 與 Claude Code 使用 `/cd <feature-checkout>` 接著 `godev`，並提供指向實際功能筆記的編輯器建議。其他主機在該處重新開啟；工具裡執行 shell `cd` 不會切換主代理工作階段。

功能筆記預設位於其工作目錄內的 `.agentflow/features/search/search.devlog.md`。生命週期操作不存取 main 的根筆記、封存與認領，即使它們忙碌也一樣；實際 Git 衝突與目標功能認領仍需處理。

`merge-feature search` 會驗證並整合，保留工作目錄與分支，除非你明確加上 `and cleanup`。適用的核准關卡會在破壞性清理前完成；main 的無關檔案與暫存內容會保留。

`drop-feature search` 表示放棄功能。主代理先檢查未合併工作與本機檔案，再移入已驗證可復原的垃圾桶／資源回收筒，移除登錄與分支。無法證明可復原就停止，不改用永久刪除。

drop 在聊天回報，不需要永久退役紀錄。已有功能筆記時，移除前會將其狀態標為已放棄／已退役；不會建立替代筆記。

在目標功能內可省略 drop 的名稱，不用先切回 main。完成後照 main 交接繼續。已合併／放棄的功能已退役；部分失敗請用確切復原動作，不要重建路徑或重做整套操作。

建立與合併使用功能紀錄。精確交接與復原見[代理功能規則](../references/features.md)。

## 在終端機使用功能指令

CLI 會寫入功能筆記：建立時儲存準備紀錄，合併時儲存生命週期進度與完成結果，drop 在移除前更新既有功能筆記的退役／清理 STATUS。drop 不另建永久紀錄。

這些產生的紀錄支援英文與繁體中文；其他語系會在變更前停止，交由主代理依設定語系撰寫，不會改用英文筆記。終端機原始診斷可使用英文。

想直接在終端機操作時，可用功能 CLI。它需要 Node.js 20+、Git（合併需 2.38+，以使用 `merge-tree --write-tree`）與唯一且現行的標準專案設定；設定需遷移或有歧義時，會停止並交由主代理處理。這些指令不存取 main 的根筆記、封存或認領。

- `agf drop-feature [name] [--abandon]`（別名 `dropft`）預設只移除已合併、且沒有已追蹤、未追蹤或忽略檔案資料的功能。加上 `--abandon` 才明確允許放棄未提交或未合併內容。目標認領與 Git 鎖定仍會阻擋移除。

  若保留的 CLI 合併留下生命週期紀錄，請依提示執行 `agf merge-feature <name> --cleanup`；其他本機資料仍須先處理。

- `agf merge-feature [name] [--cleanup] [--check '<JSON argv>'] [--include <checkout-relative-path>]`（別名 `mergeft`）整合功能，保留 main 無關檔案／暫存內容，並排除根紀錄。預設保留工作目錄與分支，加上 `--cleanup` 才清理。可重複提供 `--check` 的字面引數陣列，例如 `--check '["node","--test"]'`，不經 shell 解譯。未指定時使用合併候選內容根 package.json 的 test；兩者都沒有時仍會合併，並明確標示未設定儲存庫檢查。選定的檢查會在候選內容與整合後的 main 執行，失敗仍會阻擋完成。

  可重複加上 `--include <checkout-relative-path>`，明確授權只提交指定的未提交工作檔案與功能紀錄。產品檔案有未提交變更卻未獲此授權時會停止，並顯示 `--include` 續作方式；其他檔案與暫存項目保持不變，不會掃入所有檔案。

- `agf new-feature <name> [--open]`（別名 `newft`）從 main 已提交版本建立受管理工作目錄與功能筆記，保留 main 未提交工作。可續作完全吻合的未完成準備，不重複歷史。`--open` 開啟該筆記；編輯器啟動失敗只警告，已建立功能仍保留。

  設定 `ag.json` 頂層 `default-editor`（預設 `"vscode"`，執行 `code`）。可設為非空白執行檔名稱（如 `"vim"`）或完整路徑（如 `"/opt/my editor/bin/edit"`）；筆記路徑以單一參數傳入，沿用終端機輸入輸出。此值不接受內嵌參數或 shell 語法。

  相對編輯器路徑以功能工作目錄為準；使用 `--open` 前，請先檢視儲存庫設定。

- `agf shell <zsh|bash|powershell>` 輸出呼叫端目錄切換函式，供檢閱／複製；不會安裝或升級綁定。

merge／drop 只有在自己的已登錄受管理功能內才可省略名稱。程序已結束或認領已過期，都不會自動轉移所有權。已退役功能不能繼續開發。失敗或結果不明時保留復原資訊；先檢查並依確切下一步處理，不要重複破壞性操作。

真正的合併衝突由 Codex 在獨立候選工作目錄處理。`workspace-write` 限制寫入，不能證明作業系統層級的讀取隔離；解析器仍可能讀取較廣範圍。候選工作區排除根紀錄，指示禁止存取外部內容，並不代表 main 無法讀取。

CLI 會在整合前獨立檢查變更路徑、未解決項目與必要測試。缺少關卡核准或擁有者決定時，停止交由主代理續作；程序成功不代表合併正確。

必要檢查由操作者選擇；候選檢查在只有追蹤檔案的獨立工作目錄執行，沒有原本安裝的相依套件。適用時可依序提供 `--check '["npm","ci"]' --check '["npm","test"]'`。每個選定的檢查與衝突解析各有 10 分鐘上限；逾時會阻擋完成並保留恢復狀態。Gitlink 有變更時會在生效前停止，交由主代理處理。

`auto-commit` 與 `auto-push` 預設都是 on，合併可提交並推送 MAIN。沒有遠端時略過推送；只有一個遠端可使用，選擇有歧義時停止。這不授權發佈版本。

已確定停止、且尚未整合的檢查／解析器失敗，修正後可明確重新要求執行。不明、未停止或 main 部分生效的結果需主代理釐清，不會隱含重試。Windows 的 `--open` 需要可直接執行的編輯器；預設值可能因 `code.cmd` 啟動限制只回報警告；成功建立的功能仍保留。

要自動切換呼叫端目錄，請檢閱 `agf shell <zsh|bash|powershell>` 輸出的函式。符合條件的首次設定會新增缺少的綁定；既有綁定需明確要求升級。詳見 [shell 設定](../references/setup.md#agf-command-setup)。函式保留一般輸出，只讀取獨立且成功的目的地檔案。

建立與移除結果的各輸出區塊之間會空一行。成功建立並切換目錄後，目前產生的函式會建議在該處開啟 coding agent，省略 `cd` 指令。既有綁定在明確升級前，仍會顯示接續操作指令。

直接執行 Node／套件指令則顯示一次已加引號的 `cd` 指令，並建議切換後開啟代理；終端機流程不需要 coding agent 的 `/cd`。

macOS 是主要平台，清理使用已驗證可復原的垃圾桶。Windows 為盡力支援：明確功能清理／drop 可永久刪除確切目標；必要的功能 CLI 記帳也可刪除確切 UUID 自有認領與目的地檔案，不涵蓋他人認領或其他檔案；沒有 Windows 實測就仍屬未驗證。

Linux 無法證明自有認領可復原移除時，可在工作開始前拒絕執行，不只在清理時停止。這些例外僅適用此功能 CLI，不改變聊天指令或 looper 清理規則。詳見[完整功能規則](../references/features.md#terminal-cli)。

即使主線的最終檔案排除了根筆記本，原始功能 commits 仍保留在歷史中。若尚未發布的功能歷史包含受保護的根紀錄，CLI 會停止自動 push，交由擁有者處理該歷史；不會改寫歷史。

私人設定的繼承副本若與主線設定不同，CLI 會停止並請主代理處理；不會覆寫主線的私人副本。

## 用選配 looper 執行多組工作

looper 將獲准工作分成獨立 worktree 群組。組內任務依序在全新工作階段執行，獨立群組可同時進行。一般單一任務不需要它。

交給主代理編號成果、例子與應保留的保證。`prepare-tasks <request>` 保存群組計畫、佇列及精確原始需求，再停止供你檢視。

準備結果會儲存兩種執行方式，並在使用者可見的最後回覆中、收據之前直接顯示，即使 `inline-reply: off` 也一樣：在顯示的工作目錄中，先執行 `agf looper status <run-root>`、再執行 `agf looper run <run-root>`，或在對話輸入 `run-tasks`。提示會代入實際路徑；若 `agf` 無法呼叫，則顯示已驗證的安裝版 Node 入口指令。印出提示不會開始執行。

預設執行根目錄是 `.agentflow/artifacts/A-NNN-<name>/planned/`，包含 `group-NNN.md`、`queue.json`、`request.md`，由「目前工作」連到。你不必手寫佇列 JSON。

`run-tasks` 執行或接續該連結佇列；`run-tasks <run-root>` 則明確指定。`handle-tasks <request>` 合併準備與執行。

首次設定會偵測已安裝的 Codex／Claude CLI，填入 task、repair、acceptance 路徑；兩者都有時優先使用 Codex。範本提供 Codex 預設，設定時依偵測結果調整。保留既有設定與明確的原生選擇，共用 `model-family` 保存模型與 effort。偵測不代表已登入或可使用模型。兩者都沒有時，受支援的原生路徑需要在線主代理；否則回報缺少的能力。詳見[偵測預設](../references/setup.md#detected-worker-defaults)。

修復結果可由可用的已設定審查者審查，包括相同提供者，但必須另開全新工作階段。檢查、獨立審查與重新驗收仍須完成；明確且更嚴格的提供者要求優先。

Looper 執行期間，main 可以持續前進。協調程序記錄相容的向前變更，並以最新 main 為合併基礎，不必手動更新佇列基底。若 main 在檢查或落地時前進，會將已檢查結果帶入新的合併並重新檢查，保留已完成任務、已驗收修復與既有證據。切換分支、改寫歷史、落地結果不明或授權衝突仍須釐清。

進行中的 Git 操作或鎖定可能暫停落地。待操作結束後接續同一佇列，已完成任務仍會保留。

預設為 3 個工作群組、每組最多修復 2 次，由 `looper-limits` 設定。執行中的嘗試保留當初選擇，新嘗試採用本次啟動讀到的設定。CLI 每次嘗試上限 20 分鐘，逾時保留並阻擋未完成工作。

原生派工需要在線的主代理與結果信箱。關閉主代理不授權改用 CLI 或其他提供者。

相依群組等待前置群組完成檢查與整合。就緒群組依到達順序進入單一整合通道。有問題的群組暫停，其他獨立群組可繼續；透過主代理回答即可。

接續保留未完成修改，並先確認舊寫入者狀態。`request.md` 缺漏、變動或不安全時阻擋執行，不要默改已準備輸入來換工作。乾淨合併執行整體檢查，修復仍保留審查與驗收。契約文字有變更時，會對照原始授權，即使乾淨合併也須重新審查與驗收。

群組紀錄位於 `.aglite-records/`，不隨產品整合。預設執行保留工作目錄與證據；明確選用清理時，僅在執行目錄保留佇列、原始請求與群組計畫，其餘內容移入可復原的垃圾桶。執行本身不授權 push 或發布。

若從 shell 操作，依[代理 looper 契約](../references/looper.md)安裝 `agf`，使用 `agf looper run [run-root]` 或 `agf looper status [run-root]`。shell 省略路徑代表目前目錄，聊天 `run-tasks` 則跟隨「目前工作」。另見 [CLI／設定速查](CHEATSHEET.tw.md#looper-cli--依字母排序)與[保留檔案](../references/looper.md#retained-files)。

`run` 會在 stderr 顯示含時間的進度，並在 stdout 顯示最終結果。沒有新進度時，每 30 秒顯示一次等待訊息；這不代表代理持續前進，也不是預估完成時間。結果會分別列出已完成任務、已檢查並整合的群組、輸出與證據位置、已記錄的阻礙，以及繼續前應處理的事項。

區塊與進度事件間保留空行。含時間戳記的進度分成兩欄：第一欄是時間，第二欄是訊息。折行文字與審查者資訊都對齊訊息欄，並依終端機目前寬度換行。管線保留完整的懸掛縮排文字行；狀態與儲存報告保留完整的指令及路徑。

清理需要明確選用：完成後輸入 `agf looper cleanup <run-root>`，或在 `agf looper run` 加上 `--cleanup`。

清理須先確認執行已完成、所有寫入皆已停止。執行目錄僅保留 `queue.json`、佇列指定的原始請求與群組計畫（四個群組共六個檔案）。

其餘紀錄、報告、回答、已釋放的認領檔及未知的一般檔案都移入可復原的垃圾桶；成果與分支保留。

若要保存完整執行紀錄，請勿執行清理。保留的檔案仍支援 `status` 與已完成執行的重複呼叫，且不會重新建立報告。

目前清理需要 macOS，以及同磁碟區內可存取的垃圾桶。工作成功但清理失敗時，以代碼 1 結束；先解決阻礙，再重試人工清理指令。預設執行及受阻／停止的執行都保留暫存資料；詳見[清理安全限制](../references/looper.md#explicit-cleanup)。

CLI 任務會透過協調程序要求原有的獨立審查，由協調程序在任務沙箱外啟動已設定的審查者。這可避免巢狀 CLI 啟動失敗，並保留任務寫入限制、審查獨立性與原有結案程序，不增加審查階段。受阻結果會顯示代理證據與確切執行位置；執行或結果失敗另將 `failure.json` 保留在執行紀錄旁。

結束代碼為 0（完成）、2（受阻或停止）、1（錯誤）。觀察到已儲存狀態的執行會保留獨立的 `evidence/run-<time>-<UUID>.txt` 結果報告；前置驗證失敗時可能沒有報告。報告只是歷史快照，當前執行狀態仍以 `queue.json` 為準。`status` 不會改動檔案，也會顯示預定輸出、阻礙、相依群組與報告位置。worktree 內的草稿尚未整合；列出的輸出路徑不證明檔案存在。

最終結果依群組階層列出各任務，顯示已檢查成功、等待整合、受阻／失敗與未完成狀態，並附已儲存的成功摘要、預定輸出路徑及精簡阻礙原因。等待相依群組不等於失敗；寫入程序狀態未明時，會提示先確認程序。

終端摘要先列出阻礙與下一步，再列詳細輸出。TTY 輸出以亮紅色標示失敗、青色標示下一步；NO_COLOR 或 TERM=dumb 停用顏色。儲存報告與管線輸出保持純文字。Codex task/repair/review 明確選用 live 搜尋；父程序設有 CODEX_SANDBOX_NETWORK_DISABLED=1 時停用搜尋，並保留沙箱限制。

若舊 `agf` 函式將擷取的一般輸出當成目錄或可執行內容，請明確要求升級，檢閱 `agf shell <zsh|bash|powershell>` 產生的函式後，依 [shell 設定](../references/setup.md#agf-command-setup) 安全替換。使用獨立目的地檔案的現行函式可切換目錄，應予保留。不要刪除認領或略過檢查來續作。

### 查看結果並繼續失敗的群組

新工作可用 `handle-tasks <工作清單>`，讓主代理規劃並操作；既有佇列用 `run-tasks`。再次把原始清單交給 `handle-tasks` 可能建立另一份工作。Shell 指令直接操作協調程序，沒有主代理的判斷迴圈。

執行結束後開啟 `<run-root>/results.md`，查看最新衍生結果、群組／任務結果、預定輸出、阻礙問題 ID 與證據連結。`evidence/run-<time>-<UUID>.txt` 保留每次執行的快照。當前儲存進度請用 `agf looper status <run-root>`：報告可能落後於仍在執行的佇列。

`results.md` 只更新已驗證屬於該次工作的自動產生檔案。擁有者檔案、已編輯報告、已登記輸入、預定輸出及不安全路徑都會保留並顯示警告；獨立快照仍保留。若曾註記報告，請主代理先改名保存，再繼續同一佇列，便可恢復自動更新。

報告失敗不改變執行結束代碼。明確清理會回收兩種報告，清理後重跑不會重建。

任務顯示已檢查，表示通過任務檢查；群組還須檢查並整合，輸出才送達目標。阻礙不會抹除先前成功的任務。相依群組等待；共用狀態安全時，獨立群組繼續。

例如 G01/T01 通過、T02 受阻，可請主代理：「查看此佇列的阻礙與證據，修正已授權的技術原因，再繼續同一佇列；只有你無法決定的事項才問我。」主代理先確認實際原因、寫入程序與 Git 身分；單純重跑不會重新開啟已記錄為受阻的群組。

主代理透過 `<run-root>/inbox/answers.json` 提供已驗證的技術修正，使用 status 顯示的精確問題 ID：

```json
[{ "id": "QUESTION_UUID_FROM_STATUS", "answer": "已驗證的技術修正與證據", "source": "host" }]
```

這只是格式範例，不可未診斷就提交。主代理保留原有項目並填入實際發現。僅限擁有者回答的問題，直接用自然語言回答主代理，由它以 `"source": "owner"`（也是預設值）傳入原文。平常不必自行編輯此檔案。需要時才提供 inbox 目錄／檔案，不是規劃階段必備產物。

下次 `run-tasks` 或 `agf looper run <run-root>` 依問題 ID 匯入回答，重新開啟該未完成任務或整合。先前成功工作保留，支援時重新檢查已存候選結果。

相同回答可重複讀取，衝突替換會被拒絕。回答本身不會修好原因，也不能證明程序已停止。

未結束的原生指派還須實際停止證明；參閱 [inbox 契約（looper.md，第 119 行）](../references/looper.md#119)。

「繼續」是沿用保留工作，不是回滾儲存庫或全部重做。合併衝突的修復／審查有上限（預設 2 次修復）。失敗任務、供應者錯誤與逾時沒有通用自動重試／退避；可能需要技術修正與另一次執行。身分不明或外部效果不確定時，仍可能需要人工調查。

在線主代理可在既有授權內診斷技術阻礙、操作 inbox 並繼續。

`handle-tasks` 不會建立常駐監督程序、在主代理關閉後接手，或保證自動修復。

原生工作需要在線主代理；純 CLI 執行不需原生派工。兩者都未證明能可靠完成 1,000 個無人值守任務。

原因未明前保留證據，不要清除認領或改寫佇列來強行推進。

## 有意識地調整設定

設定放在 `<checkout>/<ag-dir>/ag.json`，通常是 `.agentflow/ag.json`。可以要求修改指定欄位，或自行編輯；缺少一般欄位會採預設值。目前設定 schema 是 13，與套件版本分開。

`use-lang` 控制新增的人類文字，包含範本標籤與收據。未設定時採作業系統語系，再以 `en-us` 備援；輸入使用哪種語言不會自行選定。明確的回答／成果語言要求優先。

原始輸入、歷史、機器語法與既有成果語言保持不變。改設定不會翻譯過去紀錄。

`auto-commit`、`auto-push` 預設 on，彼此獨立。不想自動交付時請要求兩者都 off；除非禁止 commit，前述限定的初始提交例外仍適用。

已驗證任務修改與你的其他修改分開提交，也受初始提交後的既有內容排除規則約束。Git 交付不授權部署、發布、對外訊息或無關修改。

`saving-mode` 必填，預設 off。遷移將缺少的值補為 off，保留已有 on/off。開啟時減少可省略文字／紀錄並重用證據；可理解性、要求的細節、必要檢查、關卡與復原仍保留。它不改模型或路徑。

`pipeline-roles` 與 `model-family` 為已選工作設定模型／effort，本身不啟動工作。已選設定不受支援時會阻擋，不默默替換。

Copilot 請先看[選擇速查](CHEATSHEET.tw.md#copilot-選擇)。連結的 [Copilot 代理規則](../references/copilot.md)說明傳輸控制；CLI 成功不代表原生編輯器支援已驗證。

全部值與預設值見[速查表](CHEATSHEET.tw.md#agjson--switches--依字母排序)，精確要求見[代理設定規則](../references/configuration.md#discovery-and-validation)。

## 遷移與安裝

[Agentflow 8 差異比較（英文）](agv8-agv9-comparison.md)說明保留的功能、移除的執行期強制檢查，以及遷移影響。

可相容的已知設定會保留使用者選擇進行遷移。未知／較新 schema、舊新欄位衝突與來源不明時，先等待決定。設定遷移不會默默搬移歷史或已安裝 skill。

辨識到 Agentflow 8 輸入才載入獨立程序。安全對照可自動執行，舊核准政策、認領衝突或無法保留的限制則等待。可辨識的舊欄位即使位於支援的較新標記下，仍要釐清。

確認 V8 來源且省略 `threeways` 層級時，保留有效的 `better`；明確層級維持不變。主代理更新設定與目前狀態，只移除已確認的舊專案 hooks／啟動單元，保留歷史、其他設定與可還原私人原始檔。

先前 aglite 的 schema 9–12 升到 13。缺少 `saving-mode` 時補 off，已有 on/off 保留。例如 `skip-wip: off` 對應 `omit-wip: off`，保留原意而非套用缺省預設。

先讀保存的結果，若已載入舊整合則重新啟動。舊執行中佇列／stream 需先完成或交接，不能直接變成新 looper 佇列。精確對照見[代理遷移規則](../references/legacy-migration.md)，以及[後續格式維護](../references/upkeep.md#automatic-migration)。

每個主機選一種安裝方式，依[套件 README](https://github.com/agfnow/agentflow#install) 的對應方式更新。安裝或更新後請開啟新工作階段。替換前須明確核准能保留未完成修改的具體做法，包含原始碼 checkout 或符號連結安裝。

`next_update_date` 到期時，主代理查詢一次 Agentflow 穩定版資訊，再排到兩個日曆日後。Agentflow 8.x 不是 v9 或先前 aglite beta 的升級版本。找到更新不授權替換或發布；詳見[代理版本查詢規則](../references/configuration.md#session-release-check)。

## 理解限制，並維護文件

agentflow 依靠主代理遵守指示。檔案已安裝、路徑正確，不代表自動探索、無人接手續作或所有主機都受支援。一般工作不需要 hooks 或背景執行器，初始化命令、looper 與終端機功能 CLI 是限定的執行程式例外。

Windows looper 需要 Node.js 20+ 與 Git for Windows。請依[代理 Windows 規則](../references/windows.md)操作；其他平台的測試不證明原生 Windows 或提供者／編輯器行為。

瀏覽器流程預設使用 Stagehand 與 Browserbase `browse`，你的工具偏好與專案規則優先。主代理依[代理瀏覽器測試規則](../references/browser-testing.md)檢查實際行為與存取範圍。

行為改變時，相關現行文件、範例與翻譯一起更新。每個事實有權威來源，摘要對照檢查。沒有文件影響就不另建文件紀錄。

`advisors: product-docs` 可協助文件地圖、交接或重大落差。建議不授權發布，精確維護要求見[代理規則](../references/product-docs.md)。
