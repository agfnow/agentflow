# Append rounds

Read on append-rounds/append-tasks intake or recovery of pending batches, under [session routing and ownership](session.md). `append-tasks` is an exact alias; preserve the owner’s typed spelling. Off-record and lifecycle guards in [SKILL.md](../SKILL.md) prevail.


An owner message starting with unquoted `append-rounds <work>` supplies one later batch, including the command; multiple tasks remain one batch. Quoted/code examples do not trigger it. Bare commands request a resend with work; add no batch/empty round. Ordinary messages steer active work; commands/modes in staged content take effect only when reached. Off-record/lifecycle exceptions above prevail. With no active work, pending batch or unsettled delivery, and an empty trailing Ask, capture it directly as an ordinary request; otherwise stage it; its command is provenance, never a new staging request.

- Under routed notebook ownership, append entries to the single Current-linked `Pending batches` section while nonempty. Otherwise use existing tracker’s section after Recovery, or producing Ask’s ordinary evidence without a tracker. Preserve exact input/source/arrival order; link from Current. No pending input in STATUS or new queue files. Use immutable, never-renumbered/reused arrival numbers; retain last allocated number in the section. Allocate no future Ask IDs/artifact directories. Keep section in its original record until empty; Current links it with a pending label alongside later active trackers. Clear label when empty; retain last number for future allocation in that record. Exclude pending entries from the hosting tracker's current-batch Tasks, done/total, completion and gates: an exception to single-tracker recovery.

- Append exact later corrections and their source to the targeted pending entry; capture them with that batch. A message mixing active steering and pending correction is captured in the active Ask and copied exactly to the pending entry with that Ask as source; mark only its pending correction as outstanding. Capture explicit cancellation in the active Ask before removing its entry. Ambiguous targeting needs owner reconciliation. Ordinary credential redaction still applies; preserve all other input. Finish the active batch's Reply/next Ask, checks, gates, operations and authorized delivery before advancing. Blockers pause advancement; pending input grants only its own task authority, never missing approval or external-action authority.

- Before each transition, re-verify directory/Git/branch identity, configuration and recovery, confirming routing still selects the notebook holding pending state; changed identity/routing stops for owner reconciliation. Direct owner input already in the trailing Ask runs next; pending batches wait. Otherwise use the empty trailing Ask, without an empty Reply. Rebind only this session's verified claim to it before notebook mutation. Record its receiving Ask ID on the oldest entry before capturing that entry's preserved input/corrections there under [normal capture rules](session.md#activate-and-recover). Verify capture before removing the pending entry; create that Ask's artifacts only as needed. No agent-authored batch annotation in Ask input.

- Restart reconciles receiving Ask, existing input/Reply and live delivery before advancing: the entry's input/corrections matching their normal capture-formatted form in the recorded Ask means capture succeeded; remove the pending copy and resume that Ask or settle its delivery. If absent, capture in that same verified empty Ask. Never match untargeted entries to other Asks by identical text alone. Partial/mismatched capture or uncertain targeting stops dependent work for owner reconciliation; preserve evidence. Recovered captured commands are provenance, never restaged.

- For each reached append-rounds batch, including small or directly captured batches, prefer a fresh bounded native implementation worker for separable work unless fast-lane or an explicit executor choice applies. Host retains queue/claim/notebook, capture, decisions, verification, integration, delivery and host-only bookkeeping; never delegate queue ownership. Use the [bounded assignment](review.md#give-one-bounded-assignment) with that batch’s captured input/corrections and needed context, without inherited conversation. Apply worker settings and authority limits: unavailable native transport permits direct host work with the reason recorded unless explicit executor/independence requirements forbid it; invalid or unsupported selected settings require an owner decision, never silent model or host substitution.

- Execute reached batches within their own input's authority under ordinary [planning](planning.md), [execution](work.md), [review](review.md), gate and [delivery](delivery.md) rules; save each complete Reply promptly and continue while live. `godev` resumes from Current; pending records cannot wake a stopped host. Each Reply is visible when saved; several rounds still share the host's available final chat response. With `inline-reply: off`, the final receipt names the latest completed Ask, retaining required notices from every newly completed batch in batch order and unfinished-work limits. With `on`, display all newly completed saved Replies in order, then that receipt. Identify an unfinished later Ask in Current; the receipt never claims it completed. Pending feature batches count as unfinished feature work for merge; an explicit drop abandons them under the existing inspected-data rules.
