# Product documentation

Apply to affected maintained guidance within authorized work, or an explicitly requested documentation/handover pass. Historical records are evidence, not current guidance; generated docs follow their established source. Reuse existing files, contracts and task evidence. No fixed suite, universal audit, periodic job or new approval gate.

## Reader roles and ownership

Cover needed roles in existing pages; split only for a concrete reader need, across tools, libraries, services, sites and other products:

- **Overview:** Current capabilities, intended users, prerequisites/entry point, limits and links by reader goal.

- **Manual:** First success and common tasks, expected results, likely failure/recovery, and roles/configuration only where relevant.

- **Quick reference:** Frequent supported actions/recipes linked to exact guidance; check repeated runnable syntax against its owner.

- **Maintainer guide:** Verified architecture/source entry points, a representative request/data or execution lifecycle, persisted state/external boundaries where present, change locations, affected guarantees/checks and relevant operations/recovery. Separate intended contracts, observed implementation and unproved behavior.

- **Contributor/agent guidance:** Standing work rules and links to the technical entry point/contracts; avoid duplicated architecture or feature lists. Give walkthroughs an explicit tutorial/manual role.

One page may cover several roles. Preserve established public paths/links; reorganization, deletion and publication need their own authority. Living contracts own current guarantees; link the system registry rather than copy it.

Give each changing documentation fact one owner grounded in accepted contracts and product evidence. Link volatile details instead of duplicating them; necessary summaries/cheatsheets remain checked dependents. Reuse an existing ownership index. For multi-document suites needing a map, use `<ag-dir>/doc-ledger.md` (default `.agentflow/doc-ledger.md`), never a second manifest or required public link. A tiny suite can use an ownership section in its maintainer guide.

Per indexed page, record path/audience/job, owned facts and linked dependents, semantic update triggers/source areas/proving checks, and private/generated/distributed/language relationships. Do not copy feature catalogs, defaults, command lists or invariants into the ledger. Revision evidence belongs in existing task records, without per-page timestamps, hashes or currency badges. A private ledger cannot be a dependency of shipped guidance.

## Maintain and prove

1. For a changed documented fact, inspect its owner/dependents and the actual maintained suite; the index is a discovery aid, never proof of completeness. No impact creates no record. A missing first-time suite is a named handover gap, never automatic setup.

2. Replace stale guidance in place; update the owning page and affected examples, summaries, translations and contributor/agent instructions alongside behavior. For affected fields/output tokens, explain meaning, type/allowed values, default, effect, interactions and safe edits where applicable, with a realistic example when needed. Refresh generated pages through their source; respect external/distribution authority. Ordinary host maintenance requires no advisor.

3. Search the maintained suite for the old name/value/behavior and contradictions, including undeclared walkthroughs and relevant out-of-band edits. Check affected links/anchors and concrete examples. Required reading must be accessible on the intended distribution surface; private or unavailable checkout files cannot be shipped dependencies. Exercise changed user journeys or maintainer lookups when needed; reuse unchanged passing observations. Check the actual installed/hosted/public surface when implicated and authorized; source links alone prove no UI or packaging claim.

4. Record checked scope, observations and limits once in existing evidence. An affected contradiction blocks that outcome; unavailable required access leaves it unproved. Continue independent work; unrelated drift stays a proposal, not a suite rewrite.

When implicated questions or failed attempts reveal reader confusion, preserve reader wording and group by missing concept; prioritize blocked first use, irreversible mistakes and false trust. Put the durable answer in its owning guidance and check that readers can find it; retain question → answer section → check in existing task evidence. No new ledger or wider historical audit follows.

Read [authoring](product-docs-authoring.md) for authorized first-suite/new reader-role authoring, requested substantial page/journey rewrites, or full passes/handovers; use the same trigger for advice within accepted consultation scope. Apply methods only to relevant reader needs within that scope. Ordinary changes stay focused on affected facts/dependents and do not load authoring. This reduces drift; it does not continuously enforce synchronization or prove arbitrary outside edits correct.
