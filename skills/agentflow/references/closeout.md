# Review and closeout

Read this file in full before deciding review requirements, requesting review, preparing the final Reply, or closing a round. Startup-only activation does not load it.

## Completing a round

- Presentation checks are advisory in every route: wording, Markdown styling, section order, and label placement must not block writing or completion, require cosmetic repair, or cause passing tests/reviews to repeat. Report the warning and continue. Required content, current evidence, record identity, scope, review verdicts, and truthful delivery claims remain substantive checks; prose labels alone do not prove them.

- Reread the current Ask through end of file before writing. Save each requested answer in the final Reply with enough detail to stand alone, including results, evidence, limits, decisions, questions, and next actions. A reference to an earlier screen response does not preserve its answer; for example, a request to explain each command needs those explanations in the Reply.

- For deliveries with multiple reports, persist a concise **Key Records — read these first** guide in the final Reply before closeout. Put the label on its own source line, then put each document link and its explanatory sentence on a separate source line, with exactly one blank line after the label and between entries. Indent the entries to remain within the guide's list item. Link every generated or updated report the owner needs to read, give one sentence explaining what each contains or why it matters, and order the links by recommended reading priority. Keep intermediate or superseded reports out of the primary guide unless the owner needs them to understand a material limitation. Place the guide within the relevant numbered answer under [FINAL REPORT]; preserve the existing Reply format.

- Supply Reply content starting with `## [SUMMARY]`, then `## [FINAL REPORT]`, and real questions under `## Questions (batched — each with a suggested default)`. The writer supplies `# ← Reply / A-NNN`, timestamp, and an empty Questions section when omitted; `agf close` alone adds the next empty Ask scaffold. Do not include that scaffold in `reply`. Existing fully headed Replies remain supported.

- `log-verbosity` controls only future RUN and WIP records; it never suppresses the Ask or complete Reply, and it does not relax tracker, review, test, or other closeout evidence. `inline-reply: on|off` is independent of that setting: `on` saves the normal Reply and displays that saved Reply after successful closeout or delivery, while `off` retains the path-updated acknowledgement. Successful `agf close` returns `display: { inline_reply: boolean, text: string }`; use `display.text` only after successful closeout/delivery, with the exact saved Reply when inline display is on and `<notebook> updated` otherwise.

- New Reply stamps are generated from the active session’s latest local transcript turn at write time. Codex identity requires matching session and working-directory evidence; never use config.toml, an earlier turn, or the globally newest transcript as a fallback. Missing, conflicting or unsupported evidence is labeled `<host>/unknown`; Claude currently has no verified effort extractor. Existing historical Replies and saved retry stamps remain unchanged.

- Keep `[SUMMARY]` as short outcome-first bullets covering the result, important warning, and owner action. Organize `[FINAL REPORT]` as a numbered list in the same order as the owner's requests. Give each request its own numbered item that starts with a short restatement of the original task or question, then nest its answer and relevant evidence underneath. Use explicit sequential numbers (`1.`, `2.`, `3.`); bold text may supplement the numbered label but must not replace it. Separate results, evidence, and limitations into short nested bullets with one idea per item. For a task, explicitly state whether it succeeded, failed, or remains limited, including any problem encountered. State whether the requested behavior worked and whether delivery finished; identify material limitations and distinguish earlier from current results. Keep essential evidence beside conclusions and lengthy technical evidence behind the main explanation. Do not repeat the summary mechanically. Before delivery, apply `references/writing.md`'s opening-and-evidence author check to the devlog answer. The section name `[FINAL REPORT]` does not invoke standalone-report formatting; report TL;DR/BLUF guidance never replaces the devlog's numbered groups and bullets.

- Do not use a fixed evidence-and-delivery checklist. Combine tests, review, and delivery into concise result bullets; retain exact fields consumed by checks. Omit the redundant literal `Host gate: PASS`; retain the actual host inspection and consequential structured `host_gate` evidence.

- List real questions with explicit sequential numbers (`1.`, `2.`, `3.`). Under each question, indent `- Suggested default:` and one empty `- ans:` bullet to align with the question text, leaving a blank line between items. Use `- None.` when there is no question.

- Compose the close manifest in memory and pipe a single-quoted heredoc to `--manifest-stdin`, without base64, `btoa`, `TextEncoder`, or temporary files. Never create a `close-manifest.json`. Close with one `agf close --manifest-stdin`; never add `--repo` or push without `--push-authorized`. Supply factual RUN bodies and Reply sections; the writer owns numbering and time. — I-073/I-077.

- The local close manifest has exactly this shape. This example assumes `poem-zh-tw.txt` was saved and read back in a fresh Git repository, setup-created `.gitignore` and `ag.json`, and no RUN saved yet. Keep the actual artifact filename and report only checks performed; example evidence is not evidence for your run. Adapt values to startup and observed results; this example does not classify other changes or waive their review. Include unsaved RUN bodies here; use `run_events: []` only when none remain. For an unborn repository, use wording that stays true after success rather than leaving “none yet” in STATUS.

```json
{"version":1,"notebook":".agentflow/devlog.md","ask":"A-001","run_events":["- Saved poem-zh-tw.txt and read it back; content matches the requested Traditional Chinese poem."],"reply":"## [SUMMARY]\n\n- Saved the Traditional Chinese poem in poem-zh-tw.txt.\n\n## [FINAL REPORT]\n\n1. Persist a zh-tw poem in file\n\n   - Succeeded: saved poem-zh-tw.txt and verified its content by reading it back.\n\n```completion-metadata\nInformational document: poem-zh-tw.txt — standalone poem; no executable behavior or operating instructions\n```\n","status":{"project":"poem-example","notebook":".agentflow/devlog.md","notebook_kind":"root","current_commit":"local delivery recorded in Git history","tests_scenarios":"poem content read-back","config_path":"ag.json","host":"codex","validation":"validated","proven":"Traditional Chinese poem saved and verified","open":"none","next":"await the owner","artifacts":"poem-zh-tw.txt","archived_eras":"none","streams":[]},"allowed_paths":[".agentflow/devlog.md",".gitignore","ag.json","poem-zh-tw.txt"],"commit_message":"persist Traditional Chinese poem","delivery":{"mode":"local"}}
```

  Run `node <skill-dir>/scripts/agf.js close --manifest-stdin <<'AGF_JSON'`, then the JSON and bare `AGF_JSON`. Include setup-created `.gitignore` and `ag.json` in `allowed_paths`. JavaScript renders `# STATUS`, the exact field order, fixed punctuation, schema wording, and empty-stream wording from the structured object. — I-077.

- In a plain folder, use `delivery.mode: local` with the same manifest. Closeout validates and saves the notebook without a commit, reports `commit.state: not_applicable`, and supports retrying the same manifest. Git-target review, commit, and push checks are inapplicable; retain tests, host review, and notebook checks.

- Completion rechecks repository state. A plain folder works even without Git installed; repository metadata with missing or broken Git is an inspection error, not permission to skip Git evidence. Fix that error before retrying. Local delivery inside a Git repository retains its Git checks.

- 語言設定適用於一般回覆及進度說明；`status.validation` 的 `validated`、`archived_eras` 的 `none` 等機器值仍保留固定格式。使用者在對話送出 `lang: zh-tw` 等設定要求時，透過設定工具保存並驗證 `ag.json`，無須重啟；詢問這個指令的用途不等於要求切換。

- `allowed_paths` 依本輪實際授權的提交範圍填寫。範例中的 `.gitignore`、`ag.json` 是本次初始化建立的檔案；啟動前已存在或已被使用者修改的檔案，不能只因出現在範例就一併提交。任何實際要提交的檔案，都必須納入提交前檢查；有效的純語言差異由分類器判定，其他設定變更仍遵守原有審查規則。

- Push mode adds `remote` and `branch` and requires `--push-authorized`. Successful `agf close` is the final preflight for its committed candidate.

- Independent review covers substantive changes to behavior, tests, configuration, operating instructions, verdicts or evidence when the effective policy requires it. Routine documentation and cosmetic changes do not trigger a separate review merely because a file was added or edited; the host inspects their effect first. Review informational work only when requested or materially harmful if wrong. An explicit owner instruction to skip or cancel final review waives the separate reviewer for the current Ask; no special syntax, additional justification, or reconfirmation is required. The round linter and stop hook must honor that waiver without requiring a review report or PASS. Before the first closeout attempt, check that a clear owner waiver is recognized. For contextual wording the detector cannot recognize, preserve the owner's exact text and add a clearly labeled host-recorded `skip-review: <owner instruction and context>` control; do not wait for a failed closeout to normalize existing authorization. Never infer a waiver from a hypothetical example. Other required checks remain active. — I-079.

- Host review checks correctness and scope: compare final changed paths and behavior with the accepted request and retained requirements, look for unnecessary additions and unintended reversions, and resolve or report deviations before delivery. A review waiver skips only the separate reviewer; record `Host review: PASS — <inspected scope, evidence and findings>` after this inspection. A `review-policy: prefer-independent` availability fallback instead uses the `host-review` record below, including unavailable routes and limitations. The linter and stop hook require this self-review when no separate review is available; never substitute a host-review PASS claim for independent acceptance under `require-independent`, an explicit second-reviewer request, or an enforced read-only requirement.

- **Review record v1:** Use one JSON `Review record:` line in the single `completion-metadata` fence, mutually exclusive with legacy `Cross-check implementation`, `Cross-check review`, and `Host review` lines. The record contains `version: 1`, `kind` (`external-review`, `native-review`, or `host-review`), `reviewer`, `host`, exact `source` (`{kind: "git", commit}` or bounded `{kind: "no-git", files: [{path, sha256}]}`), `report`, PASS `verdicts` for `outcome`, `minimality`, and `conformance`, `independence` facts for separate reviewer, context, permissions, family, and enforced read-only status, a nonempty `limitations` list, and observed `transport` facts for a separate reviewer. A host record also includes `unavailable: [{kind, reason}]` with exactly one reason for each permitted separate kind. Use the existing metadata writer and preserve legacy reports and waivers; do not handwrite stored completion files.

- Before review, name the qualifying changed path. Run `scripts/cross-check-plan.js` from current facts and dispatch its read-only review. The reviewer tests a plausible deletion, combination, or reuse, records the exact source commit, and returns Outcome, Minimality, and Conformance. A sufficient smaller design is Minimality: BLOCKING. Use the planner's `narrow`, `targeted`, or `full` depth; `stronger` raises one level. Current pipeline acceptance can satisfy this gate. Notify the owner when review is ready. — I-067/I-079.

- Exact notebook and tracker records are bookkeeping, not the whole workspace. Before invoking the review planner, inspect ordinary document and trivial edits and record `Non-behavioral change: <path> — <reason>` in the Reply for each change that affects no executable behavior, operating instruction, verdict or substantive evidence. The existing `Informational document: <path> — <reason>` remains valid for informational Markdown/text. The host supplies this classification without making the owner request a waiver; never infer it from filename, subject matter or diff size alone. If no review-eligible changes remain and review was not requested, do not run the planner or dispatch a reviewer. Source and evidence changes require a real current Git review target, not two matching invented commit claims.

- Before the first `agf close` attempt, inspect every final changed path, including run records created after the implementation commit and supporting briefs, dispatch logs, and result/verification records created during or after review; add a per-path `Non-behavioral change` classification in the Reply metadata only when the record merely preserves the same reviewed facts. Changes to executable behavior, operating instructions, verdicts, or substantive evidence still require current review, with no blanket artifact-directory exemption; accepted passing tests and review may be reused for purely record-only additions.

- Supply applicable machine fields once in one `completion-metadata` fenced block in the closeout draft, after the human report and before Questions. The writer saves the evidence and its integrity information under `$workspace_dir/.tmp/` and removes the whole block from the published Reply. The devlog contains no generated completion-record link, hash, metadata fence or hidden metadata comment. Never handwrite or edit the stored record. Include one Review record v1 or the legacy Cross-check implementation/review and waived Host review fields, plus per-path classifications; omit the block when no fields apply. Keep human results and concise validation outside the record.

- Retain completion records at closeout. The writer, checker and stop hook resolve new records from the exact notebook and Ask through the same reader; missing, corrupt or mismatched records cannot supply completion evidence or an assumed pass. Preserve support for legacy links and inline fences without rewriting historical bytes. Cleanup is disabled by default; when enabled, the stop hook attempts a locked Trash-only sweep at the configured interval (default seven days), preserving active, retrying and still-needed records. Only proven completed inactive records older than 30 days qualify; failures do not advance the last-success time. Ignored local records do not travel with a clone, and trashed records must be restored before their evidence can be rechecked.

- Preserve field meanings: exact 40-character review commit and report path for legacy external evidence, a substantive Host review PASS reason when separate review is waived or unavailable, and one exact path with a short factual reason per necessary classification. Do not repeat the same field or classify the same path twice, inside or outside the block. Legacy plain Reply records remain readable; ordinary example fences, quoted text, and indented code do not supply completion evidence. Never rewrite historical rounds for this format.

- Write each classification as one plain line inside the metadata block, using `Non-behavioral change: <path> — <reason>` or `Informational document: <path> — <reason>`. Do not add styling or replace exact paths with directory-wide exemptions.

- A change to Agentflow record locations sets `workspace_layout_change: true` and supplies `workspace_instruction_inventory` with the six governing skill, stream, pipeline, looper, English-guide, and Traditional-Chinese-guide files required by `cross-check-plan.js`.

- After the review PASS, independently inspect its report and evidence. Consequential work then needs current Result Go for the exact implementation commit.

- Closeout stop rule: after current implementation tests and review pass, record-only corrections need only the mechanical completion check. Do not rerun already-passed implementation tests or reviews unless source, tests, behavior instructions, verdicts, or substantive evidence changed. Repeated final validation of unchanged implementation is a protocol defect, not progress. — I-072/I-073/I-079.

- Supply STATUS values in the manifest's `status` object; JavaScript renders its fixed fields. Keep the result within 60 lines. — I-077.

- Run `terminal-preflight.js` only for manual/recovery closeout without `agf close`. Do not repeat it after successful `agf close`.
