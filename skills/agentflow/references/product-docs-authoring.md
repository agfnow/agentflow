# Product documentation authoring

Use only under [documentation guidance’s authoring trigger](product-docs.md#maintain-and-prove). That reference owns scope, authority, roles, ownership/doc-ledger and maintenance proof; this file adds scoped methods, not a fixed suite or workflow. Reuse existing pages and task evidence; apply each method where relevant to accepted reader needs.

## Establish boundary and reader gaps

- Inspect relevant product/contracts, docs, help, configuration, tests, examples, manifests and known limits before claims. Establish audience, prerequisites, supported environments, distribution, required versus optional parts/accounts/providers, installation boundary, first useful result, what the first action creates, human decisions, automatic steps and unsupported edges. Missing access permits a labelled plan, not invented behavior.

- From relevant available questions, issues, support/devlog records and failed attempts, preserve reader wording; group by missing concept and rank consequential dead ends over cosmetics or frequency alone. Reuse the maintenance question → answer → check trace; no observed questions means no invented user evidence or forced friction ledger.

- Diagnostic hints: first action → tutorial route; handoff → actor timeline; artifact identity → creator/state map; overview-to-reference gap → lifecycle; trust → failure/check explanation; field meaning → configuration reference; capability → extension/limits; migration → semantic differences; missed existing answer → reader-worded headings/navigation; drift → owner/distribution checks.

## Teach and explain

- Lead with the reader’s problem/outcome and route by goal. Put the first usable action beside recognizable success; teach one main path before options. Identify actor/action/result, adding state change and likely recovery when needed. Show a controlled failure where it teaches a consequential boundary; finish with a concrete next route.

- Trace a representative object/request through applicable creation, storage, transformation, verification, failure, revision and completion. Explain relevant artifacts/components: purpose, creator, consumers, lifetime/location, source/configuration/state/evidence/generated/demo/history kind and contract owner.

- For multiple actors, show automatic actions, separate invocations, pauses and who acts next. For verification claims, explain check/review independence and limits, what scripts versus semantic review versus human judgment establish, and claim → failed check/refutation → correction → fresh evidence → success where relevant. Explain consequences of failed checks/review without inventing product guarantees.

- For human and machine forms of one concept, name their audiences, authoritative/enforced source, synchronization and disagreement consequences. Keep known limits visible with one owner; distinguish defects from intentional boundaries.

## Make references usable

- Cover every public command, option, field, environment variable, output token, state location, extension point and error class readers must interpret within the authorized reference scope. Use the foundation’s field explanations with realistic safe-edit examples; explain identifiers, statuses, abbreviations, colors and demo-only output when meaningful to readers.

- For promised extension seams, give sufficient realistic examples to explain supported use; distinguish local customization, product-source changes and unsupported extension. Use readers’ wording for FAQ headings; explain troubleshooting through symptom → cause/diagnosis → safe recovery → escalation where available.

- Reuse established fact owners. For new suites, possible homes are help/task reference for syntax, reference/schema for configuration, contracts for durable shapes, tutorial for first run, conceptual guide for relationships, maintainer guide for source/change entry points and history for rationale. These are roles, not required files: overview need not enumerate options, tutorials need not copy full references, FAQ need not copy schemas and history must not compete with current instructions. Split only for a demonstrated reader need.

## Check the scoped result

- Connect in-scope reader gaps to exact maintained answer sections and checks; no empty “see docs” or “document later” substitutes. Keep needed map/ownership changes, resolved gaps, observations, unverified assumptions and remaining limits once in task evidence; use normal delivery for the owner-facing result, not a new mandatory report.

- For an authorized full pass/handover, check all needed reader roles, relevant distribution and high-value historical questions. Rehearse the applicable newcomer path from intended shipped guidance: fit/prerequisites → install/first success → explain the lifecycle → likely failure/recovery → field meaning → who acts next/next goal. Preserve the foundation’s execution/distribution checks and access limits.

- Label simulated reader checks as simulated; they test explanation/findability under stated conditions, not real-user comprehension or unperformed runtime behavior. Investigate stalls: repair in-scope documentation gaps, distinguish product/access failures and retain missing proof. Use real newcomer observations when available without inventing evidence or adding a reviewer/agent stage.
