# Planning and task contracts

Read before deciding whether actual work needs a design/tracker, or authoring/materially revising a plan. Ordinary Q&A requires no execution/design contract. Task modes remain in [work](work.md#task-modes).

Apply [planning modes and gates](#planning-modes-and-gates) before task edits. Under optional, one bounded reversible outcome with a known approach needs only the devlog result/next action and retained proof; apply the creation criteria below otherwise.

- Unless fast-lane waives creation, multiple outcomes/to-dos, delegation or interrupted work require a tracker before execution; `must` includes bounded actual work. One bounded reached append-rounds batch delegated alone is exempt, not other criteria/requests/gates. Capture every accepted item; split only usefully. Multi-part behavior changes need a design unless `off`. Login/permissions, private data, destruction, payments or external sends need both before implementation under these creation rules (`off`: tracker only), plus independent adversarial review before accepting the changed boundary unless skip-review/fast-lane waives it. Discussion/plan-only delivery triggers no boundary review.

- Save requested plans before implementation. Plan-only grants none; “plan first and wait” stops there; “plan and implement” continues unless a material decision remains. Keep unauthorized future work/optional proposals outside accepted tasks. Apply [gates](#planning-modes-and-gates).

Before authoring/materially revising an already-needed plan, design, specification or task grouping, read [planning routes](review.md#planning-routes) for proportionate selection, worker controls, explicit/configured 3ways, fallback and synthesis. Reuse matching plans/checks/review and recovery evidence; routes create no planning requirement. [Work](work.md#task-modes) owns task-mode precedence; preserve scope, plan-only stops and gates. Read [review](review.md) before result review or worker dispatch, and [Copilot](copilot.md) only on a Copilot host or selected Copilot route/profile.

- **Design:** implementable without reconstructing conversation: original Ask/authority, retained requirements/exclusions, approach, paths, applicable behavior/interfaces/data, failure/recovery and open decisions. State decided public fields/types/defaults/required states/errors once. Separate owner decisions, observations, assumptions and suggestions; approval supplies neither access/credentials nor unobserved proof. Required sections: `## Invariants`, `## Acceptance criteria`, `## Validation`, `## Minimality check`. Stable `INV-n`: starting condition, preserved guarantee, failure. Stable `AC-n`: observable pass/fail examples, proving check, required environment. Map every requirement to design section and AC/INV IDs; Validation names exact checks/evidence/limits without duplicating contracts. Suite names alone are not acceptance. Scale to complexity/risk without missing relevant contracts or inventing production work.

- Before edits and at closeout check adequacy → scope → minimality. Accepted outcomes/purpose/constraints/safeguards are pass/fail; simplify only adequate in-scope approaches. Additions need an accepted outcome, constraint or concrete blocking failure, never hypothetical needs. For removals/replacements name retained guarantee, replacement and proving example; fewer parts/words prove nothing. Count implementation, human/host attention, coordination, verification and recovery burden. Run authorized checks, expose missing proof; request decisions only for unresolved authority/outcome/constraint choices before dependent changes. Explain lost outcomes; reopen settled decisions only on new conflicting evidence. Derive grouping/paths/dependencies/checks from owner goals/constraints/examples and evidence; ask material unknowns only.

- Before implementation compare plans/designs with original inputs/accepted decisions, not merely replacement contracts: coverage, invariants, acceptance/proof, conflicts/open decisions. Consequential architecture needs compact responsibility flow, one concrete lifecycle and a check rejecting the inadequate alternative before expensive pilots; include ordinary human intake where relevant. Distinguish executable-loop permission, dispatch during host absence and control of ordinary task events where relevant; settling one settles no other. Keep proportional per-task checks in [Round evidence](session.md#round-evidence), pre-implementation contract checks in that contract; no extra document, mandatory alternative, review stage or implementation authority. Preserve checkpoints. After design changes assess durable guarantees under [system invariants](invariants.md), recording the decision in Invariants without duplicating policy; refresh affected contracts/checks after scope changes.

- **Tracker:** accepted goal/overall state/reason/done-total → `## Tasks` → `## Recovery` → evidence/update details. Task heading: `- [<status>] T-n — <short outcome>`; labelled nested fields, blank-separated. Only `TODO` (not started), `DOING` (includes pending checks/review/delivery), `BLOCKED` (name blocker), `DONE` (proved); no checkbox/`pending`. Stable ID order; Recovery identifies current task/next action. Each task retains request/source, outcome, exact paths/boundary, decisions/dependencies, resolved contract/implementation choices or links, acceptance/INV IDs, proving evidence link, failure handling and next action. Link shared contracts; retain every accepted unfinished outcome/correction, separating deferred ideas.

- Recovery: actual update time, current item, last proved result, blockers, actual running handles/none, expected paths, next safe action. Refresh after scope changes, milestones/checkpoints and before completion; compare actual changes to scope. Derive done/total from items; DONE needs requested observations. Overall completion requires all accepted tasks proved done, no blocking decision, required check/review/delivery, task-owned operation or authorized action outstanding. Checkpoints do not stop execution: continue authorized unfinished work unless owner stop/checkpoint, missing authority/access or exhausted host budget; record reason/next safe action.


## Planning modes and gates

- `plan-mode`: optional (default) uses ordinary criteria; must creates scoped design.md and tracker.md before authorized edits; off creates no design (nor renamed substitute), permits needed trackers. Read/maintain existing contracts/checks/review/risk safeguards/recovery. Requested plans may use existing tracker/Reply; keep plan-only stops. Setting alone creates no idle/off-record/setup/lifecycle-preparation/Q&A/staged-batch records; isolated task work follows it. Explicit task instructions override without persisting settings. Apply task modes first: fast-lane waives must creation unless owner explicitly requests planning; configured gates/checkpoints prevail.

- Before edits, `off` + `gate-design on` is a named settings conflict: stop dependent work, request a choice, suggesting optional or gate-design off with explained consequences.

- Cases: must + one-line authorized fix → both records; optional + bounded fix → proportional records; off + login change → tracker/independent review, no new design; off + gate-design on → conflict; must + idle/off-record/setup/lifecycle/Q&A → no setting-driven records; must + fast-lane → creation waiver unless explicit planning.

- `gate-design on`: save concrete design, pause before implementation for owner approval; optional/must creates it, off requires conflict resolution, never implicit waiver. Prior explicit approval of the same design suffices; material contract changes need renewal. Continue independent authorized work; defaults/empty answers approve nothing. off adds no checkpoint.

- `gate-tracker on`: if a tracker exists, after all execution/checks/review pass, pause before final Reply/release, delivery commit/push. Present checked result; save approval request/pending action in tracker/Current or linked report, retaining open-round claim, no final Reply/next Ask. State awaiting release approval, not complete. Explicit approval of the same checked result suffices; then perform authorized pending release actions without repeating unchanged checks. off adds no checkpoint.

- For merge-feature, command-authorized feature snapshot/merge commits are prerequisite integration operations after feature verification; then check combined main. Gate pauses before destructive cleanup, final feature-record delivery commits, push/handoff. Keep state/claims only in feature records, never root main notebook. Prerequisites waive no final approval; failed integration cannot reach gate. Requested stops/checkpoints prevail.
