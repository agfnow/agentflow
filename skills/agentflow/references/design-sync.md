# Design synchronization

- An unquoted `design-sync [scope]` starts a read-only inventory. Use an unambiguous affected component family, token or icon when scope is omitted, otherwise ask for scope. For a [closeout offer](delivery.md#notebook-and-delivery), list concrete items supported by existing findings without starting a new inventory or delaying the task’s delivery.

- Compare relevant authorized design-system assets, Storybook or other component catalogs, Figma and code. Stay within the selected scope and authorized access. Identify the accepted source of truth, current revisions, maintainers, supported variants and known consumers by affected product. Flag unexamined areas, conflicting authority and intentional exceptions. Propose reuse, consolidation, addition, retirement or icon/token synchronization where supported.

- Save the proposed items in the [devlog approval question](delivery.md#questions-during-work). Give each item a stable ID, artifact and source revision, exact change, reason, affected consumers, dependencies and proposed check. Ask the owner to list approved IDs and any item-specific instructions in the answer field. Link the saved question from Current for recovery and label closeout offers as optional follow-ups. A command, closeout suggestion, default, silence or approval of another item grants no sync authority. If nothing is actionable, report the inventory result and stop.

- Apply only selected, expressly approved items with the required write/publication authority for each destination. Recheck the saved approved items, instructions, dependencies and current sources before effects. Defer items with unmet dependencies. Return materially changed, unclear or expanded items for renewed approval. Keep unapproved items pending under the saved question. Verify applied changes against their approved behavior and supported variants, and report applied, deferred and blocked items. Existing approval, delivery and external-action rules still apply.
