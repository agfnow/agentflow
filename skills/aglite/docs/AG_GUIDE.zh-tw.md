# aglite 9.0.0-beta.1 — 日常使用指南

[English](AG_GUIDE.md) · 繁體中文

aglite 讓代理把需求、決定與結果留在專案裡。下次開啟對話時，可以從紀錄接著做，不必靠你重講一次。

你仍然用自然語言交代工作。aglite 會依工作大小安排紀錄、計畫、檢查與審查；不需要每次跑完整套流程。

這份指南說明日常用法。要查完整指令、設定預設值或顧問角色，請看 [CHEATSHEET](CHEATSHEET.md)。

## 先完成一件小事

在專案目錄開啟已安裝 aglite 的助理，輸入：

```text
godev 修正 README.md 的安裝步驟，並確認範例指令與目前檔案一致。
```

本文把你正在對話的程式代理稱為「主代理」。它負責理解需求、協調其他代理、核對成果與保存結果。

第一次使用時，主代理會建立缺少的設定與紀錄。已有紀錄就沿用，不會整批覆蓋。

若這個資料夾還不是 Git 專案，主代理會先問你要不要建立 Git repo。回答不要也能繼續；沒回答就等待，不會代你決定。

同意建立 Git 時，會先建立空白初始 commit，再做其他初始化。這不會把你原本的檔案順便提交；若你明確禁止 commit，就略過，並說明功能工作目錄需要先有 commit。

初始化也會在根目錄 `AGENTS.md` 補上主代理預設載入 aglite 的指示，保留原有規則。支援並遵守這項指示的助理，之後可直接接手；找不到 skill 時會回報，不會自行安裝。

安裝與初始化是兩件事。還沒安裝時，先依[套件 README](https://github.com/agfnow/aglite#install)選擇適合你的方式。

## 換個對話，也能接著做

下次在同一個專案開啟對話，輸入 `godev` 即可接續。它會先看目前需求、待回答問題與復原連結，再核對實際檔案狀態。

有未完成工作時，會從安全的下一步繼續。有核准關卡或缺少權限時，先等你的決定；沒有工作時，就請你提出下一個需求。

你可以直接在聊天回答問題，也可以填寫紀錄中對應的 `ans:`。空白答案、建議預設值與等待時間都不算同意。

如果主代理說筆記已被另一個工作階段認領，請先確認誰正在使用。它不會只因標記很舊就刪除或搶接；需要你明確授權交接。

## 答案與紀錄在哪裡？

預設紀錄目錄是 `.agentflow/`，可由 `ag-dir` 改成其他安全的專案相對路徑。以下範例都使用預設位置。

日常筆記通常是 `.agentflow/<專案短名>.devlog.md`。例如專案資料夾叫 `a002`，就是 `.agentflow/a002.devlog.md`；已有自訂名稱則繼續使用。

每一輪都有你的「提問」與主代理的「回覆」，並以 `A-NNN` 識別。筆記開頭的「目前工作」欄位指向接續位置；想看完成了什麼，先找最新的「回覆」。

預設 `inline-reply: off`，完整答案存進筆記，聊天結尾只留下這種收據：

```text
→ 已更新: A-001 | .agentflow/a002.devlog.md
  (~/project/a002)
```

收據的路徑告訴你去哪裡讀。若專案設定使用其他語言，收據文字也會跟著變。

想讓完整答案也出現在聊天，可以要求將 `inline-reply` 設為 `on`。只想這次顯示，請明確說「請在聊天貼出這次的完整答案」；改變未來顯示設定或談論輸出範例，不等於要求顯示目前答案。

必要通知、未完成工作的阻礙與實際功能交接仍會出現在聊天。若初始化時沒有指定工作，完成後會請你提出下一個需求。

### 其他檔案各有用途

`design.md` 說明要做什麼、保留哪些行為，以及如何驗收。`tracker.md` 列出待辦、進度與復原資訊；兩者都按需要建立。

追蹤事項使用 `TODO`、`DOING`、`BLOCKED`、`DONE`。等檢查、審查或交付仍是 `DOING`；`DONE` 代表已有完成證據。

有用的測試、審查與除錯證據另存，通常在 `.agentflow/.tmp/A-NNN.md`。筆記保留結論與連結，不塞滿技術日誌。

`.tmp` 的名稱不代表可以刪除。仍被引用的證據必須保留；接續工作時應從「目前工作」找連結，不要猜檔名。

`backlog.md` 收集未來可能要做的事。`proposed` 是建議，`deferred` 是已接受但延後；記下來不代表授權執行。

想挑下一件事，可以說「幫我看 backlog，建議下一項工作」。主代理會說明理由、相依關係與大致工作量，等你選定才安排。

`sys-invariants.md` 保存已接受、後續修改仍應維持的系統保證。內容改變時，主代理會在紀錄與聊天明確通知；空白登錄檔不代表已有獲准的保證。

筆記超過 750 行或你要求封存時，較早完成的輪次會附加到相鄰的 `<筆記名稱>.archive.md`。未解決工作與最近完成的一輪會留下，既有歷史不重寫。

紀錄與復原細節見[工作階段規則](../references/session.md)及[交付規則](../references/delivery.md)。

## 途中補充，還是排到下一批？

一般訊息用來修正或補充目前工作。例如「也要保留舊連結」會成為目前任務的條件。

想排在目前工作完成之後，另送一則訊息：

```text
append-rounds 更新英文安裝指南。
```

再另外送一則：

```text
append-rounds 檢查兩種語言的範例是否一致。
```

一則訊息就是一批，裡面有多個事項也仍是一批。`append-tasks` 是同義指令，不會把工作加進 looper 佇列。

主代理會先完成目前這批的回答、核准與交付，再依序為後續批次建立各自的提問／回覆。有阻礙就暫停；`godev` 可以復原尚未執行的批次。

不要把 `new-feature`、`merge-feature` 或 `drop-feature` 混進後續批次。功能操作請獨立送出，其餘工作再另用 `append-rounds` 安排。

取消某批時，直接說明要取消哪一批。完整規則見[後續批次](../references/batches.md#append-rounds)。

## 這次不想留下紀錄

在訊息加上未引用的 `nolog:`，這次交流就不讀寫工作流程筆記，也不會被補進後續摘要：

```text
nolog: 請在聊天解釋這段設定。
```

`noop:`、`off:`、`skip:` 都是同義寫法。`noop:` 仍會執行你授權的工作，不是預演。

效果只限這次交流；下一則沒有標記的訊息恢復記錄。單純引用這些文字當範例不會啟用。

不要把不留紀錄標記和 `append-rounds` 放在一起。這種請求不會被排入，也不會執行；需要你移除標記後重送。

## 依工作挑選做法

一般任務不用指定模式。主代理會依需求、風險與證據，選擇足夠的做法。

### 小修改：fast-lane

```text
fast-lane 修正 README.md 的錯字。
```

這個任務由主代理直接完成。略過一般委派、顧問、額外獨立審查、新設計／追蹤文件與例行進度段落，仍要檢查成果並保存需求與答案。

你明確要求的計畫、審查與核准關卡仍適用。模式持續到這件事完成，包含中途補充與接續；不會變成專案永久設定。

### 只由主代理審查：skip-review

```text
skip-review 調整這份使用指南的段落順序。
```

這件事仍保留原本的規劃與檢查，只將一般獨立審查改成主代理審查。它也豁免這套 skill 一般要求的風險邊界獨立審查。

這個指令取代同一任務先前的使用者審查要求；同一則或之後另有明確審查要求時，以新要求為準。效果在任務完成後結束。

### 先把需求問清楚：grill-me

```text
grill-me 我想讓新使用者更快完成第一次設定。
```

主代理先看已有背景，再用小輪問題釐清目標、重要假設與最值得質疑的地方。通常每輪一至三題，附上選項、影響與建議，依你的回答追問。

至少會有一輪讓你確認或修正理解；重要意圖不必再猜時就停止。這只授權訪談，不會順便授權實作，也不會建立永久模式。

### 已有程式碼，需要深入理解：browfield

```text
browfield 為現有登入流程加入第二種驗證方式，保留原本的使用者行為。
```

`browfield` 的拼法就是指令名稱。它選用八步驟，從理解現有程式、還原規則與風險，到建立基準、規格、實作、驗證與保存結果。

適合不熟悉的既有程式碼，尤其需要避免回歸時。不是只要專案已有程式碼就自動啟用，也不必另裝 skill 或找八位顧問。

原本的任務模式、核准與審查仍適用。詳見 [browfield 指引](../references/browfield.md)。

### 有特定問題，再請顧問

```text
advisors: requirements, explore
```

顧問提供聚焦建議，例如釐清需求、理解陌生程式、比較方案或檢查資安。主代理也會在發現需要深入調查的實質問題時選用，不會每件事都載入所有角色。

顧問建議不是擴大實作範圍的授權。完整角色清單見 [CHEATSHEET 的顧問說明](CHEATSHEET.md#commands--alphabetical)。

需要發佈前稽核明確候選版本時，可用 `advisors: final-audit`。它在一般檢查與產物組裝後判斷就緒程度；即使得到 GO，仍不代表你已授權發布。

## 計畫、審查與核准怎麼配合？

預設 `plan-mode: optional`，簡單且可逆的單一工作通常不另建設計。多個成果、需要委派或中斷後要接續時，通常需要 tracker；多部分行為變更通常需要 design。

`plan-mode: must` 要求實際修改前建立 design 與 tracker。`off` 不建立新 design，但有需要仍可建立 tracker；已有契約、必要檢查與審查仍要遵守。

只要先規劃，請說「先做計畫，完成後等我決定」。這不授權實作；如果你說「規劃後實作」，主代理會在重要選擇已解決且沒有關卡時接著做。

### 想比較計畫，可用 3ways

```text
3ways plan 調整設定檔的探索方式。
```

Claude 先根據完整需求與獲准讀取的來源提出主計畫，Codex 再挑戰具體缺陷，最後由主代理整合。只有高信心且有證據的缺陷才改變主軸，個人風格偏好不算理由。

這不是一定要湊三個代理，也不是實作核准。一般已需要的規劃預設 `plan-order: external`；可用路徑與失敗後的選擇見[規劃路徑](../references/review.md#planning-routes)。

### 檢查與審查是不同工作

主代理先核對成果與必要測試。變更程式、操作提示、產品成果或可直接實作的契約，通常還需要另一份成果審查；一般問答由主代理檢查。

預設 `review-order: external`，先嘗試對應的外部 CLI，再嘗試全新上下文的內部代理，最後才由主代理審查並揭露限制。明確要求獨立審查時，沒有合適路徑就仍是待處理，不能自行當作通過。

選到的模型或推理設定無效時，會指出問題並要求決定，不會悄悄換掉。審查方法與模型設定見[成果審查](../references/review.md#inspect-the-finished-result)。

### 需要你點頭時，就設核准關卡

`gate-design: on` 讓主代理先保存具體設計，再等你核准才實作。它與 `plan-mode: off` 衝突，必須先選擇要保留哪個設定。

`gate-tracker: on` 在有 tracker 的工作完成檢查與審查後，等你核准才做最後交付。沒有 tracker 就不會因此新增一個關卡。

兩個預設都是 `off`。沒有回答不算核准；已核准且沒有實質改變的相同結果，也不用反覆再問。

完整條件見[規劃與關卡](../references/planning.md#planning-modes-and-gates)。

## 把一個功能分開開發

Git worktree 是同一個 repo 的另一個獨立工作目錄，擁有自己的分支與檔案。你可以在那裡開發功能，保留 main 的現場。

```text
new-feature search
```

這會準備 `.wts/ft-search` 與 `feature/search`，並建立功能專屬筆記。只有建立指令、沒說要做什麼時，不會自行開始實作。

主代理會列出已建立的位置、切換方式與實際筆記路徑。Codex／Claude Code 的接續操作形如：

```text
/cd .wts/ft-search
godev
```

請照實際交接訊息操作。其他助理可能需要在該目錄重新開啟；工具內跑 shell `cd` 不代表目前對話已經切換。

功能筆記預設在 `.agentflow/features/search/search.devlog.md`。功能生命週期不讀寫 main 的根筆記與認領標記，因此 main 筆記忙碌或尚未完成，不會單獨阻擋它；實際 Git 衝突與目標功能的占用仍要處理。

### 完成後合併

```text
merge-feature search
```

主代理會驗證功能、整合到 main，再檢查合併結果。預設保留功能 worktree 與本機分支；若也要清理，請明確說：

```text
merge-feature search and cleanup
```

設定的最終核准關卡會在破壞性清理之前完成。main 原有的工作檔與暫存內容會保留，根筆記、封存與認領變更不會從功能分支一起帶入。

### 不要這個功能了

```text
drop-feature search
```

這表示放棄指定功能。主代理先檢查未合併內容與本機資料，再將工作目錄移到可復原的垃圾桶／資源回收筒，移除 worktree 登錄與分支；無法證明可復原時就停止，不改用永久刪除。

放棄功能的結果只在聊天回報；不會另外寫入功能筆記。

已在目標功能目錄內時，可只輸入 `drop-feature`，不必先切回 main。完成後照交接訊息回 main；已合併或放棄的功能不能繼續開發。

合併或清理中途失敗時，保留現場，使用主代理提供的確切復原指令。不要另建同名目錄或直接重做整個操作；詳見[功能規則](../references/features.md)。

## 工作多了，再考慮 looper

looper 是選用的多組工作協調方式。每組在獨立 worktree 依序做事，不相依的群組可以同時執行；一般單一任務不需要它。

先給主代理編號工作清單，說明預期成果、例子與必須保留的行為：

```text
prepare-tasks 將這三項工作分組，保留各項驗收條件，準備好後停止。
```

`prepare-tasks` 只準備，不執行。成果放在 `.agentflow/artifacts/A-NNN-<名稱>/planned/`，包含 `group-NNN.md`、`queue.json` 與保留原始需求的 `request.md`，由「目前工作」連到執行根目錄。

確認準備結果後，用 `run-tasks` 執行或接續；也可指定 `run-tasks <run-root>`。想直接準備再執行，改用 `handle-tasks <需求>`。

### 執行前要有路由設定

範本的 `looper-routes` 是空的，必須先選定 task、repair、acceptance 的執行方式、提供者與模型目錄。主代理會協助確認，不需要你手寫佇列 JSON。

模型與推理設定仍放在 `model-family`，不放進佇列。選新任務路徑時優先考慮外部 CLI；你明確選定的原生路徑與既有嘗試不會被擅自替換。

預設最多同時執行 3 組，每組最多修復 2 次。可在 `looper-limits` 修改；執行中的嘗試保留當初選擇，新嘗試才採用這次啟動讀到的設定。

CLI 任務每次啟動新的短期程序，只帶該任務需要的背景，完成後才啟動下一個。原生派工需要在線的主代理；關掉主代理不會自動改用另一家提供者。

### 查看問題與接續

有問題的群組會等待，你回答主代理即可；其他獨立群組可以繼續。有相依關係的群組，則等前置群組完成檢查與整合才開始。

完成的群組依就緒順序逐一整合。乾淨合併執行整體檢查；修復仍需審查與驗收。

中斷後用 `run-tasks` 接續，先確認舊寫入者已停止，並保留未完成內容。CLI 每次嘗試上限 20 分鐘，超時會留下現場與阻礙，不算成功。

原始 `request.md` 遺失、變動或路徑不安全時，執行與接續會停止。不要直接修改已準備好的輸入來改變任務；請讓主代理處理新的需求。

群組紀錄放在各自的 `.aglite-records/`，不隨產品合併。結束後 worktree 與紀錄仍保留；清理、推送與發布都需要各自的授權。

需要從 shell 操作時，可依[執行契約](../references/looper.md)安裝 `agf`，使用 `agf loop run [run-root]` 或 `agf loop status [run-root]`。shell 省略根目錄時找目前目錄；聊天的 `run-tasks` 則找「目前工作」所連的佇列。

## 設定只改需要的部分

專案設定放在 `<checkout>/<ag-dir>/ag.json`，預設為 `.agentflow/ag.json`。缺少欄位會使用預設值，不必把每個選項都寫進去。

語言由 `use-lang` 決定；沒有設定時先取作業系統語系，再用 `en-us` 備援。用中文發問不會自行切換語言；可以明確要求這次回答或成果使用繁體中文。

`auto-commit` 與 `auto-push` 預設都是 `on`。主代理會分開提交已驗證的任務修改與你的其他修改，並先確認安全的遠端與分支；這不授權部署或發布。

不想自動提交或推送，可以直接說「把 `auto-commit` 和 `auto-push` 都設為 `off`」。關掉推送不會關掉提交，兩者是分開的。

`saving-mode: on` 會減少可省略的文字與文件，重用仍有效的證據。它不會略過必要檢查、核准與可理解的說明，也不改模型或路由。

代理角色與模型對照分別放在 `pipeline-roles` 與 `model-family`。需要 Copilot 或自訂目錄時，請先確認實際主機支援哪些控制；設定名稱本身不代表某個模型、effort 或原生派工已可用。

全部 switch、預設值與模型設定入口見 [CHEATSHEET](CHEATSHEET.md#agjson--switches--alphabetical)及[設定規則](../references/configuration.md)。

## 舊設定、安裝更新與平台限制

相容的已知舊設定可依已記載的對照遷移，保留有效的自訂選擇。未知版本、舊新欄位衝突或來源不明確時，先請你決定，不會重設成範本。

設定遷移不等於搬移歷史紀錄，也不等於替換安裝。更換安裝必須先取得明確同意；若來源是符號連結、原始碼 checkout 或有未提交修改，要先提出能保留工作的具體方式。

遇到可辨識的 Agentflow 8 專案時，主代理才會載入獨立的遷移提示。能明確轉換的設定會自動升級；舊核准規則、認領衝突或無法直接保留的限制，會先等你決定。

升級會調整專案設定與目前狀態，移除確認屬於舊版的專案 hooks 或啟動指示。對話歷史、其他工具的設定與可還原的私人備份都會保留。

aglite 的 schema 9、10、11 也能升級成 schema 12。例如 `skip-wip: off` 會保留原意，改為 `omit-wip: off`，不會套用缺少欄位時的預設值。

完成後先看保存的遷移結果。若目前工作階段已載入舊 hooks，請重新開啟助理；仍在執行的 v8 佇列或 stream，則要先完成或交接。

詳見[舊版遷移規則（legacy-migration.md，第 1 行）](../references/legacy-migration.md)。升級專案格式不會自動覆寫已安裝的 skill；替換安裝內容仍須你明確同意。

更新方式請依[套件 README](https://github.com/agfnow/aglite#install)與原本的安裝方式處理，每個主機選一種方式。aglite 是 Agentflow 9 的 beta 名稱；Agentflow 8.x 不是它的升級目標。

主代理依 `next_update_date` 檢查 Agentflow 穩定版資訊。日期到期時才查詢，之後排到兩個日曆日後再查；發現更新也不會自動替換安裝。

一般工作不需要 hooks、排程器或背景執行程式；looper 是選用的協調程式例外。完成與復原仍依賴主代理遵守指示，不能保證關掉對話後還會繼續做。

Windows 的 looper 需要 Node.js 20+ 與 Git for Windows。支援的啟動方式與可復原清理限制見 [Windows 指引](../references/windows.md)；其他平台的測試不能證明原生 Windows 已通過。

網頁工作預設使用 Stagehand 與 Browserbase `browse`，但你的工具偏好與專案規則優先。涉及實際瀏覽器操作時，會依[瀏覽器測試規則](../references/browser-testing.md)檢查操作結果與存取範圍。

## 改了行為，也要更新說明

若工作改變了使用者、貢獻者或維護者需要知道的行為，相關現行文件、範例與翻譯應一起更新。沒有文件影響，就不必另建一份文件紀錄。

每個變動事實有一個權威來源，其他摘要與翻譯對照它檢查；不強制每個專案使用相同文件組。需要釐清產品全貌或重大文件落差，可用 `advisors: product-docs` 請顧問聚焦建議。

詳見[產品文件維護](../references/product-docs.md)。
