# Feature worktrees

Local commands: `new-feature`, `merge-feature`, `drop-feature`; quoted examples do not execute. Use Git directly, no hooks/runner. Perform only the requested operation. Keep creation/merge recovery state in feature-local records; drop results belong in chat, with no durable retirement record or replacement ledger. Trackers follow planning/gate requirements. `merge-feature` retains branch/worktree unless cleanup is explicit (e.g. “and cleanup”), authorizing both checkout retirement and merged local branch deletion.

Follow [configuration.md](configuration.md); `.agentflow` means configured `ag-dir`. Route all three lifecycle commands here before generic notebook activation/recovery. Never read, claim, recover, capture input in, update or close main’s root notebook/archive, including an inherited copy; never inspect or alter its claim. Its absence, content or ownership cannot block lifecycle work. Do not checkpoint/release even this session’s main claim for these commands. Main Git/configuration and feature-specific records remain usable; real Git locks, overlapping product edits and target-feature claims remain blockers. Mixed unrelated work follows normal routing separately. Read applicable project rules and invariant registries; lifecycle commands author no main shared-record adoption/backlog/registry changes. Integrating already-authorized committed feature changes to those records is feature delivery, subject to overlap checks and required invariant/backlog notices. Handoffs override inline display; preparation grants no implementation authority.

## Identity and routing

- Resolve original physical session directory, Git root/branch and registered worktrees; use absolute paths and explicit command working directories. Identify one registered local main checkout; missing/ambiguous main stops lifecycle mutations without switching branches.

- Managed layout: `<main>/.wts/ft-<name>` on `feature/<name>`; other layouts are unmanaged and require an explicit local notebook for development, never relocate implicitly. Resolve symlinks and verify exact path/registration/branch, including from subdirectories; substring matches, detached HEAD or unregistered directories are invalid. Derive identity from the branch and exact matching path (`ft-demo` uses `ft-ft-demo`), never by stripping `ft-` blindly. Stop writes on disagreement; never nest worktrees inside feature checkouts.

- Names match `[a-z0-9]+(-[a-z0-9]+)*`. Ask for missing names; merge/drop may infer only the verified current feature. Main requires an explicit target, never an old handoff. Quote arguments; owner text stays data.

- Managed feature notebook: `<ag-dir>/features/<name>/<name>.devlog.md`; round artifacts use feature-checkout `.agentflow/artifacts/A-NNN/` under [evidence rules](session.md#round-evidence). Reject a supplied root/other-feature notebook and give the correct path. Never recover answers/tasks or write to the inherited root notebook. For development or creation with a missing notebook, inspect only feature-specific notebook/archive history and retirement evidence before writes. Only explicit/repeated `new-feature <name>` authorizes interrupted preparation without a notebook; bare activation/implementation input supplies no such authority: give the main-session `new-feature <name>` handoff and stop. Never copy root work. Records are tracked relative to that checkout and reach main by merge. Unmanaged feature development requires an explicit local notebook; do not guess. Drop instead follows its missing-notebook/retry exceptions below.

- Read-only idle screening may inspect STATUS and the tail before claiming; only verified open, nonretired features may use the [idle shortcut](../SKILL.md#route-before-records), never lifecycle commands or retirement recovery. Apply [claims](session.md#notebook-ownership) only to used feature notebooks/integrated copies; never main’s root notebook. Drop requires no notebook. Activation conflicts refuse the operation; late conflicts use only [bounded recording recovery](session.md#notebook-ownership), never repeat lifecycle effects. This session's matching claims are not cleanup blockers. For new-feature, exclusively reserve its notebook after checkout creation, before config/notebook writes; retain its claim through local preparation closeout, then release only this session's claim. Before authorized Trash retirement, verify final feature records and release this session's feature claim. Never release another session's claim or edit Trash copies.

## STATUS and rejection

Read existing feature STATUS before task work at activation/recovery; drop with no notebook uses verified Git/session identity instead. Check the startup binding or verified `/cd` binding below, never a subprocess cwd. Missing paths, Trash locations, identity conflicts or known retirement stop task writes except the verified directory transition or bounded terminal cleanup of an already-authorized own-feature drop or post-cleanup merge-delivery recovery below; never recreate/fall back. If a retired feature’s notebook disappeared, use its integrated feature-specific copy or verified Git/session evidence; never main’s root notebook or a replacement retirement ledger. Missing STATUS never overrides known retirement.

- New/verified open features: `Stream: open`, `Cleanup: N/A`, `Session: active`. Initialize missing fields only after live identity checks. Main omits these fields; reading a feature record does not retire main. Refresh the shared STATUS fields under [delivery](delivery.md#notebook-and-delivery) as well.

- Successful validated integration: `Stream: merged`, `Session: retired`. Bind these to absolute checkout, branch, integrated feature tip and main merge commit. Ordinary feature work ends even if the directory remains. `Cleanup: N/A` means no cleanup authorized; `pending | failed | complete` records explicitly authorized cleanup, including uncertain/partial results. Complete requires verified Trash movement, exact unregistration and branch deletion.

- Merged/dropped features reject further development regardless of cleanup outcome. Only already-authorized terminal cleanup or final gate-controlled delivery in progress may finish there; later work requires the main handoff below. Retirement applies to the feature, not a conversation after a verified directory transition.

## `new-feature [name]`

1. Resolve main/name under the isolation rule above. A feature-rooted invocation claims/records only an existing verified open feature notebook, then hands off to main with the exact command; if absent, give that handoff in chat without initialization. Do not create there. Main-rooted preparation uses only feature-local records; main claims stay untouched. Capture the committed local main tip read-only; preserve and explain exclusion of uncommitted edits. Never automatically fetch/pull/stash or commit unrelated work.

2. Check exact target/branch/registration and configured notebook/archive history at the target, or in committed main before creation. Check retirement only in existing target-feature records, their committed feature-specific copies and verified Git/session evidence. No root-notebook history scan or permanent tombstone; after all old objects are gone, an explicit creation may reuse the name without reviving old work. Reuse only an exact registered managed pair; never reset/move/replace history; foreign feature claims block writes. Other path/branch collisions stop. Existing merged/dropped/retired records cannot be reopened; choose a fresh name when they remain. For an absent notebook in an existing exact pair, require this explicit/repeated command as preparation authority; inspect partial config/ignore changes and known history, never infer implementation or recreate a missing historical notebook. A missing/ambiguous retirement identity stops. Git inventory suffices; no pre-creation intent record.

3. If the pair is absent, use `git worktree add -b feature/<name> <absolute-target> <captured-main-tip>`. Once the checkout exists, resolve inherited/default configuration and its safe feature-local notebook path, then exclusively reserve that notebook under [notebook ownership](session.md#notebook-ownership) before initialization or other preparation writes. On reservation failure, retain/report the partial pair; never reset/remove it or clear another claim. Resolve canonical/sole inherited legacy settings in memory; dual files stop. Defer config creation/relocation until step 4 initializes the feature notebook. Ignore only the worktree container, using a narrow local-exclude rule if needed; feature records must remain tracked. For shared excludes, preserve existing bytes, append one complete newline-delimited exact rule without replacement, then reread to verify rule meaning and concurrent additions. Never record preparation in main’s notebook or write main config/inherited root tasks.

4. Initialize an absent, history-free notebook exclusively from the [notebook asset](../assets/.agentflow/devlog.md), rendering under [delivery](delivery.md#notebook-and-delivery). Populate STATUS/lifecycle fields and record exact checkout/branch, committed-main baseline and this creation request as local provenance; no main Ask link is required. After safe reservation/scaffolding, save migration proof and relocate any sole inherited legacy config only inside this feature. Create `<feature-checkout>/<ag-dir>/ag.json` from the [configuration asset](../assets/.agentflow/ag.json) only when configuration discovery finds no canonical/legacy file or unresolved candidate, without overwrite; preserve inherited configuration, resolve ag-dir before config creation and never migrate main’s live config. Check completed preparation first: verify/reuse its saved result and pending implementation without duplicate closeout or input; new requirements cannot overwrite active work. Otherwise retain open-notebook IDs/pending work: use an empty trailing Ask with no pending work, or append preparation after a closed round; resume an unfinished preparation only after matching its recorded identity/authority to this command and inspecting actual state; other occupied/unresolved tails stop for owner reconciliation, never bury work. Rebind only this session's claim to the receiving Ask before mutation.

5. Capture the lifecycle command/context in that feature-local preparation Ask using [session](session.md#activate-and-recover)'s owner-input rules; preserve the supplied implementation portion for the next Ask, not as preparation work. Preserve the whole owner request across these locations with source links, without duplicate capture. Verify identity/config/notebook/ignore behavior and STATUS, saving needed checks under Round evidence, linked from the feature notebook. Close preparation there with the verified creation handoff as Reply and append the next Ask in the same write. Put only supplied authorized implementation requirements into that next Ask using owner-input capture, with their source; name-only leaves it empty and Current/Next awaiting a request. Preserve existing input exactly once; never invent implementation, empty design/tracker or implementation results.

6. Read back Reply, STATUS and next Ask, release own feature claim after preparation settles, display the handoff and end; no implementation before the verified destination transition and no automatic commit/push. Partial failure retains exact observed Git/config/notebook state and its next safe action locally if claimed; before a notebook exists, report it in chat without a main record. Retrying absent-notebook preparation requires explicit `new-feature <name>` again.

## `merge-feature [name]`

1. Resolve target and cleanup authority separately. Feature-rooted sessions may merge only their own feature; another target requires main handoff. Main requires the name. Claim only the feature notebook and any feature-specific integrated copy before their writes. Capture the merge command in the target feature notebook’s receiving Ask (or its integrated copy for later cleanup), reconciling tail IDs/pending work under new-feature step 4 rather than burying an unfinished Ask. Require completed feature work/checks; preserve unrelated edits and inspect staged/unstaged/untracked/ignored contents. Actual target-session/lock blockers must settle before cleanup.

2. This command authorizes committing verified feature task paths and integrating them into main. Verify main HEAD is on its expected symbolic branch, with no Git lock or merge/rebase/cherry-pick/revert/bisect/sequencer operation; preserve unrelated staged/unstaged work. Resolve root notebook/archive/claim paths from pre-merge configuration, excluding their feature changes from snapshots and integration. Configuration changes rerouting those paths require an owner routing decision, never inspection/approval of the root notebook or claim.

   Use ordinary `git merge --no-ff feature/<name>` only with an index matching HEAD and no feature changes to excluded paths relative to the merge base. Otherwise use `git merge-tree --write-tree` / a disposable index and `git commit-tree` to build a scoped merge: keep main HEAD’s excluded paths and original main/feature parents; report discarded feature path/blob IDs without reading their prose. Git blob/fingerprint operations for preservation are allowed, semantic notebook/claim reads are not. Never stash/reset or replace the owner’s index. Dispose of task-owned temporary files under the deletion policy; ship no helper. Plumbing commits bypass commit hooks: disclose that and run required repository checks separately.

   Save old HEAD, feature tip, scoped merge commit and pending path updates in feature-specific recovery before mutation. Recheck the original ref, index entries and affected working paths; apply the complete scoped diff (including removals, renames, modes, symlinks/submodules) only to clean integration paths, preserving excluded and unrelated owner entries/bytes. Stop on real product overlap. Use compare-and-swap `git update-ref <main-ref> <merge-commit> <oldHEAD>` and recheck state at each update. On partial failure inspect the saved commit/parents, actual ref/index/worktree and finish only missing path/ref updates; HEAD already at that merge is not authority to merge again or reset. No notebook-owner checkpoint.

3. Validate combined main and arrival of feature-specific records. Failed/unavailable required checks retain the checkout without marking merged. On success mark only the feature notebook’s integrated copy `Stream: merged`, `Session: retired`, bound to checkout/branch/integrated tip/merge commit; mirror into its surviving feature copy. Use `Cleanup: N/A` unless cleanup was explicitly authorized, then pending. No root-notebook integration/retirement entry or Reply.

4. Satisfy any configured final gate after integration checks and before destructive cleanup or final delivery. Keep pending state/authority/identities in the feature tracker/notebook, never a main root record; approval resumes only verified pending work. **Without explicit cleanup**, retain checkout/registration/branch, close only feature Reply/next Ask after approval and report retention with no pending cleanup. Retired feature Asks carry no development work.

5. **With explicit cleanup**, save necessary authority/identity in the integrated feature-specific record, save pending source state and release this session’s source-feature claim, then run the shared retirement procedure from main with absolute paths. This bounded sequence may remove the host’s own feature checkout. Before `git branch -d feature/<name>`, require registration gone, branch tip unchanged from the integrated tip and that tip an ancestor of main. Mismatch/uncertainty stops cleanup; no blind retry.

6. Save the observed cleanup result and final Reply/next Ask only in the integrated feature-specific notebook; mirror STATUS into any surviving original after reacquiring its feature claim, without a second Reply. Complete requires every cleanup check; otherwise retain exact partial state/next safe action. Apply configured commit/push only to verified merge delivery after gates, never root-notebook or unrelated owner edits. Never deploy. Feature-rooted hosts give the retirement handoff; main-rooted hosts report the result and remain active.

### Pending delivery and later cleanup

A verified main session may finish authorized retired-feature delivery/cleanup using its feature-specific records, chat authority and live Git identities; never root-notebook state or claims. A feature-rooted session whose own checkout was removed may finish only its already-authorized terminal merge delivery using saved exact main/feature paths, integrated tip and merge commit with explicit main cwd; no development, Trash access or directory rebinding. Verify configuration, identities, feature-record ownership and prior checks; missing/mismatched evidence stops dependent work. Gates precede removal, so no post-cleanup gate requires a root claim.

For later `merge-feature <name> and cleanup`, inspect existing integration/authorization and live identities; never remerge/recommit for recovery. New cleanup authority sets pending; prior N/A grants none. Verify completed steps instead of recreating absent objects. Changed/reused paths/registration/branches stop mutation. Finish only remaining authorized actions.

## `drop-feature [name]`

1. Verify session directory, exact checkout/branch/registration and main. Run directly from inside the target feature checkout; no pre-drop `/cd`, restart or handoff to main is required. Feature sessions may drop only their own feature and may omit its name; another target requires main handoff. Main requires explicit names. A partial-cleanup retry requires an explicit renewed drop command. First reconcile any prior chat authority/exact identities with live Git and surviving paths; a verified-missing checkout/prunable registration is permitted, and a fresh command without prior chat authorizes abandonment of the explicitly named, newly reinspected remaining branch only after verifying its managed identity; already-absent matching objects are completed steps, not reasons to recreate or require a notebook. Ambiguous/reused identities stop. Inspect unmerged commits, all tracked/untracked/ignored contents, target claims and Git locks. Show authorized abandonment without reconfirming; resolve unrelated owner files. Never commit, merge or push.

2. No durable drop/retirement record is required. If a target feature notebook exists, claim it before marking only its STATUS dropped/retired with cleanup pending, then verify/release this session’s claim before removal. Missing notebooks do not block drop; foreign target claims still do. Do not copy the abandoned notebook or create a replacement ledger, report or tombstone.

3. Explicit drop authorizes terminal removal of the host’s own verified feature checkout. From main, use absolute paths: recheck identity/blockers; move the checkout to verified Trash/Recycle Bin; verify preserved recoverable contents/path absence; `git worktree remove <checkout>`; verify unregistration, unchanged inspected branch tip and no other checkout; `git branch -D feature/<name>`. Verify deletion. Stop on uncertainty; no force-removal, prune or permanent-deletion fallback.

4. Report actual Trash/registration/branch results or exact partial state/next safe action in chat, including inspected branch tip and remaining steps, regardless of `inline-reply`. Update cleanup STATUS only if the original feature notebook survives outside Trash; do not create a record to report success. Never edit Trash copies or recreate missing paths. A retry uses the renewed command, available prior chat and live identities, verifying completed steps and stopping for a fresh owner decision on evidence of changed/reused objects; no notebook or durable retirement history is required.

5. After removing its own checkout, the feature-rooted host reports the actual result and gives `/cd <absolute-main-checkout>` then `godev`; stop without probing/recreating the deleted cwd. Only the owner’s subsequent verified host directory transition resumes work. Main-rooted hosts remain active without accessing main’s notebook. Completed drops need no follow-up record/commit/push.

## Retire one worktree

- Immediately recheck exact managed path/registration/branch, distinct from main, no lock, and outside this host's startup checkout/ancestor except explicitly authorized terminal cleanup after successful own-feature integration or drop. Inspect all contents, including ignored files. Stop task-owned work only within existing authority and verify it stopped. Block for another coding session only with a foreign ownership claim or host metadata mapping a live session ID distinct from this conversation to the target. Cwd, process names, different PIDs and shared app-server ancestry do not establish session identity; idle shells and unmapped helpers do not block cleanup. Accept owner identity corrections and exclude this session and its helpers. If reliable session metadata is unavailable, skip process-based session detection; retain ownership and Git-lock checks. Never kill another session or clear its claim without explicit authority; age, silence and clean Git status do not establish release.

- Follow owner deletion policy: from main, use `trash <absolute-target>` or a verified platform Trash/Recycle Bin equivalent. Before alternative cleanup, prove recycle/restore and byte preservation on a task-owned disposable directory on the same volume, verify the actual target can be recycled and require refusal of permanent deletion; [Windows guidance](windows.md#reversible-cleanup) describes Windows constraints. Verify success, preserved recoverable contents and original path absent, then `git worktree remove <absolute-target>` to unregister only that missing checkout. No global prune/force/permanent-deletion fallback; unavailable or unproved reversible deletion stops cleanup. Inspect unknown results before retrying moves. Verify registration absent before branch deletion; failure leaves deletion pending. Never recreate/overwrite the path; Trash's `.git` link is no longer a live checkout after unregistration.

A pending gate or delivery keeps its required claims and blocks switching until settled. Preserve source notebook recovery links without copying its tasks into the destination.

Resolve a relative handoff destination against the recorded verified source directory and compare its absolute physical path. On the next message, accept a transition only when host-reported session context shows that exact destination; shell cwd, a changed tool workdir or an owner assertion alone is insufficient. Verify its physical directory, Git root/branch/registration and nonretired identity; rediscover its `<ag-dir>/ag.json` under configuration.md and project rules, route its correct notebook and apply normal activation/recovery, including the idle shortcut, before task work. This authorized handoff permits notebook rebinding under configuration’s ownership rule. The verified destination becomes the session’s directory binding, including later identity checks and receipts; retain the source only as provenance. A missing retired source does not block this verified destination transition. Wrong/unchanged host context repeats the handoff without destination writes; if host context is unobservable, use the restart fallback below. Never clear foreign claims, reopen retired features or silently fall back.
